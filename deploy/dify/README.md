# Dify 原生 IoT 应用

这套应用在 Dify 执行模型规划、HTTP 节点、对话记忆和结果校验，复用平台的业务数据与受限 MCP 工具。它不调用 DeepSeek Harness 模型运行时，不替换现有平台 AI 页面或告警后台自动研判。

| 应用 | 类型 | 行为 |
| --- | --- | --- |
| 运维助手 | Chatflow | 查询设备、告警、历史与绑定知识；按用户原话保存禁用规则草稿 |
| 告警研判 | Workflow | 查询事实，返回经校验的风险等级、置信度、原因、建议、证据和待确认项 JSON |
| 设备健康巡检 | Workflow | 输出含统计时间、优先处理设备和数据局限的巡检报告 |
| 协议接入助手 | Workflow | 按输入资料和绑定知识输出 JSON 字段映射草稿 |
| 系统状态助手 | Chatflow | 查询系统概览，区分总量与截断列表，支持多轮对话 |

## 调用链与权限

```text
Dify 输入 → 读取平台事实与绑定知识 → 模型规划补充查询
  → 受控工具执行 → 模型生成结论 → JSON 校验 / 聊天回答

Dify HTTP 节点 → Node 接入服务 → Go API /mcp/harness → 平台业务数据
```

当前接入模式是**固定租户的受信任运维工作区**，不是 Dify 用户与 IoT 用户的单点登录。获准访问这些 Dify 应用的人员可查询配置租户的设备；不要向不具备该租户权限的人员开放应用。如果需要按 IoT 登录用户的设备范围使用，应另接平台后端签发的逐次授权，不复用此工作区凭据。

每个应用有独立的随机接入凭据，只放在 Dify secret 环境变量与 Git 忽略的 `data/dify/` 中，不进入模型提示。接入服务校验来源地址、应用凭据和 manifest 工具白名单；模型不能设置租户、用户、目标 URL 或上游凭据。平台 JWT 仅存在于接入服务到 Go API 的请求头，有效期 120 秒、每次只授权实际调用的一个工具。

平台管理员登录用于校验配置租户以及读取设备清单和 Agent 知识策略。知识检索强制使用应用对应的 `workflowId`、TopK 和最低分数；禁用知识时不检索，要求证据且无召回时流程失败。规则草稿保存由既有平台工具完成，默认禁用；没有确认、关闭告警、启用规则、设备控制、SQL、shell、文件或任意网络访问入口。

HTTP 节点不自动重试写入；若用户重新运行一次规则创建请求，可能生成另一份禁用草稿，应先查看告警规则。固定工作流最多补充查询六个工具；下述原生 Agent 可以根据结果继续调用，但每次工具计划仍最多六项，权限与业务边界相同。

规则草稿沿用平台现有 `create_rule_draft` 行为，条件可能尚未限定具体设备范围。运维助手应展示实际保存内容，使用者在启用前仍需检查作用范围、阈值及动作。

这些工作流不使用 Dify Code 或模板转换节点，JSON 编解码与校验由接入服务完成，避免依赖目标环境当前异常的代码沙箱。没有关闭沙箱安全保护。HTTP 使用表单编码，用户输入里的引号、换行和 `&` 不会破坏 JSON。DeepSeek 节点显式关闭思考模式；规划及结构化结论使用 `json_object`，避免思考内容占满输出额度。工具结果提供毫秒时间戳到 UTC 的确定转换，模型结论仍需按原始证据复核。

## 准备和运行

要求 Node.js 22 或更高版本及已启动的本项目 Go API。无需安装额外 npm 包。在仓库根目录运行：

```powershell
# 按实际环境填写：Dify 容器要能访问接入服务所在机器。
$env:IOT_DIFY_PUBLIC_URL = 'http://<宿主机地址>:8092'
$env:IOT_DIFY_HOST = '<宿主机地址>'
$env:IOT_DIFY_CLIENTS = '127.0.0.1,<宿主机地址>,<Dify服务器地址>'
$env:IOT_DIFY_TENANT = 'tenant_001'
node deploy/dify/generate.mjs
node deploy/dify/gateway.mjs
```

生成脚本首次创建 `data/dify/config.json`；后续保留已有配置和密钥。需要变更环境时编辑这个本地文件，再重新生成。`envFile` 指向实际平台环境文件；进程环境变量优先。接入服务启动时会向平台登录验证租户，失败不监听端口。

通过 Dify 工作室导入 `data/dify/*.yml`，它们包含本机连接信息与秘密，**不能提交、上传公共仓库或公开分享**。`deploy/dify/apps/*.yml` 为无秘密模板。JSON 格式是 YAML 子集，Dify DSL 0.7.0 导入器支持；默认模型与插件版本来自本次工作区导出配置，可在 Dify 中按部署环境选择模型。

如 Windows 防火墙阻断连接，仅为接入端口及明确的 Dify 来源地址增加规则，不关闭防火墙。接入服务停止或宿主机休眠时，Dify 实时查询会失败；需常驻使用时，应由服务管理器运行接入服务与 IoT API，或一起迁到服务器。当前脚本不自动修改系统启动项。

若 Dify HTTP 节点被 SSRF 代理拒绝，在 **Dify 的 Compose 目录**备份 `.env` 后，将接入服务宿主机的单个 IPv4 地址加入 `SSRF_PROXY_ALLOW_PRIVATE_IPS`，例如 `<宿主机IPv4>/32`。保留已有白名单，再执行 `docker compose up -d --no-deps ssrf_proxy`。只调整必要目标，不禁用代理或放开整个内网。通过实际 SSRF 代理访问 `/health`，而不仅从宿主机直连，确认网络路径。

重启本地环境时，先在仓库根目录运行 `go run ./cmd/iot-platform --env-file .env.local`，再另开终端运行 `node deploy/dify/gateway.mjs`。已有 `data/dify/config.json` 时不需要重新生成凭据或重新导入应用。

## 工作区使用

五个应用统一以“炬联 IoT · ”开头。在工作室打开运维助手或系统状态助手，点击“预览”即可聊天；另三个应用点击“测试运行”，填写任务描述后运行。告警研判可以输入“研判最近一条告警”；协议助手需提供实际报文或字段资料。

本次部署发布了应用版本，但停用了公开 Web 应用、外部 API 和 MCP 访问点，按已授权范围供已登录工作区使用。发布版本与开放匿名链接是不同操作。若以后要接入平台页面或对外提供应用，应先配置匹配的身份和数据权限，再启用对应访问点。

## 原生 Agent 与 Skills 对比

另提供两个 Dify 原生 Agent，共用 DeepSeek V4.1 Flash 与五个受限数据工具：

| 版本 | 业务步骤来源 | 使用入口 |
| --- | --- | --- |
| 炬联 IoT · 原生 Agent 对比版 | 直接写在系统提示词中；Agent 自行选择和迭代调用工具 | Agents → 配置；工作室的“炬联 IoT 体验 · 原生 Agent” → 测试运行 |
| 炬联 IoT · Skills 对比版 | 按任务加载已发布的 Skills，再执行其中的方法 | Agents → 配置；工作室的“炬联 IoT 体验 · Skills Agent” → 测试运行 |

五个 Skills 是 `iot-operations`、`iot-alarm-analysis`、`iot-device-health`、`iot-protocol-draft`、`iot-system-status`，分别覆盖运维、告警、巡检、协议和系统概览。在 Dify 的 Skills 页面可查看和编辑；修改后需发布。Skill 是可复用的任务方法，由 Agent 加载执行，不是独立聊天应用。

目标社区版不提供独立 Agent 的预览，因此两个体验工作流均为“输入 → 原生 Agent 节点 → 输出”。实际推理、工具选择和 Skill 加载由原生 Agent 运行；每次测试为独立任务，可在输入里包含追问背景。原有两个 Chatflow 仍用于连续聊天对比。

可给两个版本输入完全相同的问题：

1. `当前设备总数和活动告警是多少？研判最近一条高等级活动告警，给出事实证据、可能原因及人工建议，说明知识是否有匹配。`
2. `巡检当前设备，区分启用、连接和数据状态，列出优先检查对象与数据局限。`
3. `将 JSON 报文 {"deviceId":"demo-01","temperature":31.2,"humidity":60,"alarm":false} 整理成字段映射草稿；温度单位为摄氏度，湿度为百分比，不发布协议。`

五个“炬联 IoT 工具 · ”工作流只返回平台事实和工具执行结果，不含模型。它们复用各业务专属凭据、知识策略和固定租户。原生 Agent 的告警/协议输出由提示词约束，未串接固定工作流的严格 JSON 校验节点；用于自动消费时优先使用已有校验的专用 Workflow。

生成和部署资料：

- `node deploy/dify/generate-agent-assets.mjs` 生成私有工具 DSL 到 `data/dify/agent-assets/`，无秘密模板到 `agent-tools/`，Skill 正文到 `skills/`。
- `provision-agents.py` 在匹配版本的 Dify API 容器内，使用 Dify 服务导入并发布工具、Skills 与 Agent 配置。先在界面创建两个原生 Agent，并为直接版选择模型；参数为 `--assets`、`--anchor-app`、`--direct-agent`、`--skill-agent`。脚本校验锚点应用及工作区归属，不适合未经核对直接用于其他版本。
- `provision-agent-workbenches.py` 使用相同参数发布两个单 Agent 节点体验入口。
- Dify 原生 Agent 首次发布会默认打开访问点，部署脚本会在发布后停用 Web/API；未生成外部 API 密钥。暂存私有 DSL 应限制访问并在部署后删除。

原生 Agent 使用 Dify 独立的 Agent 执行服务和沙箱；与上文 Code 节点的旧沙箱不是同一执行路径。

## 验证

```powershell
node --test deploy/dify/gateway.test.mjs
```

在 Dify 逐项测试：系统概览与平台统计相符；告警研判 JSON 格式有效；设备巡检注明截断范围；协议助手不虚构偏移；多轮聊天能承接设备上下文。规则创建用明确的测试请求，确认工具结果 `persisted=true` 且规则 `enabled=false`，不要为测试启用规则。

应用导入、节点执行成功和业务验收是不同结论。知识未绑定时可能零召回，应在平台知识库中绑定对应 Agent 的文档；不会自动导入 Dify 中其他业务知识库。

### 同日 Agent / Skills 对比联调

两个原生 Agent、五个已发布 Skills、五个无模型数据工具及两个单 Agent 节点体验入口已部署。两版使用相同问题实际运行，覆盖系统统计、告警研判、设备巡检、最后温度查询和四字段 JSON 协议映射；查到 8 台设备、2 条活动告警及最后温度原始值 88.5，协议仅生成草稿。Skills 版回答会注明所用 Skill，五类技能均有对应任务运行记录。

巡检复测发现设备注册接口返回 `{ device, runtimeState }`，已修正接入层显式字段映射，最终两版均列出 8 台设备的名称、ID、各类状态及缺失字段。自动化测试使用实际接口结构检查业务字段和凭据排除，10 项通过。原生 Agent 偶尔会把工具分配到不支持的业务入口；接入层会拒绝执行，并返回 `400 / allowedTools / executed=false` 帮助纠正，未放宽工具权限。

首轮生成答案出现过历史样本计数不一致；已增加统计与单位证据约束，但生成内容仍须按工具证据复核。Skills 版在本次多任务样本中有更多调用和更高 Token 用量，这不是性能基准，也不代表 Skills 天然优于直接提示。告警/协议需严格机器校验时使用上文专用 Workflow。

新增的 9 个应用访问点（两个 Agent、五个数据工具、两个体验工作流）均核对为 Web/API 关闭；部署临时私有 DSL 已从虚拟机及 API 容器移除。可重建资源与说明保存在本目录，本机部署 ID 记录保存在 Git 忽略的 `data/dify/deployed-agent-apps.json`。
