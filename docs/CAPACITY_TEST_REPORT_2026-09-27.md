# 容量压测历史摘要（2026-09-27）

本页保留当天开发环境的实测结论、后续修复复测及原始证据索引。它不是当前版本的重新验收；已实现功能和操作步骤以 [部署](DEPLOYMENT.md)、[开发与测试](DEVELOPMENT.md#容量验证) 为准。原始长报告与修复过程可从本文件 Git 历史查找。

## 初始压测与问题定位

| 场景 | 当天观察 |
| --- | --- |
| HTTP 持续写入 | 180 秒阶段最高通过档为 50 条/秒：8,934 次成功、0 失败，与窗口唯一原文和标准结果相符；100 / 200 条/秒档有失败 |
| 混合负载 | 初始通过的最高已测组合为 10 条/秒 + 1 查询并发 + 1 PDF 并发；不能换算成后续按请求速率发压的组合 |
| MQTT | 过载触发 API panic，需人工重启；158,421 次 PUBACK 未证明业务入库，5.5 万连接压力也未证明同规模持续上报 |
| PDF / 查询 | PDF 64 并发约 62.7% 超时并拖慢管理；查询风暴曾耗尽负载机临时端口，不能全部归因于服务容量 |
| 完整性 | 静默后 319,193 条原文及同数标准消息，36 条 `processed_at=0`；应有遥测 300,344，实际唯一遥测 300,336，缺失 8 条 |
| 死信原因 | ClickHouse 重试存在性检查不能解码字符串形式的 count；36 条消息产生 65 条重复死信，因此 lag=0 不代表完成 |
| AI / 大报告 | 全量数据拼接使运维报告返回 413；巡检/PDF 读大对象、事件快照和范围查询争用；告警生成速度高于 AI 完成速度 |

这些是修复前故障，不能当成当前源码仍存在同一缺陷的证据。后续针对 ACK 生命周期、应用归档确认、ClickHouse 重试与死信、巡检分页/PDF 缓存、授权聚合与快照缓存、设备状态写入、AI 输入预算及取消机制进行了修复和代表性复测。

## 修复后代表性复测

以下结果来自 [remediation.json](capacity/2026-09-27/remediation.json)，只代表指定窗口与负载组合。

| 场景 | 条件 | 结果与边界 |
| --- | --- | --- |
| MQTT 50 条/秒 | 32 个发布连接，30 秒，归档确认等待 3 秒、重试最多 2 次 | 1,497 确认、0 失败，实际 49.7 条/秒，P95 893.9 ms；4 条重试，部分时间与 race 编译重叠 |
| MQTT 100 条/秒 | 同连接/重试参数，含收尾约 39 秒 | 实发 1,925，确认 1,007，确认超时 918（47.7%），P95 9,045.4 ms；不合格，超时不等于立即判定丢失 |
| HTTP 混合上报 | 目标 50 条/秒，90 秒，同时运行下两项 | 4,491 成功、0 失败，P95 288.0 ms；结束 storage lag=3，随后排空 |
| 同时 PDF 下载 | 5 次/秒，90 秒，同一已完成报告 | 449 成功、0 失败，完整读取响应，P95 75.2 ms |
| 同时管理查询 | 事件/总览/注册列表合计 20 次/秒，90 秒 | 1,797 成功、0 失败，P95 187.3 ms；独立管理探针 180 次无失败 |
| 授权范围列表 | 总注册 101,129 台，用户仅授权 100 台；10/30/50 请求/秒，各 20 秒 | 分别 199/598/998 次成功；较早档与 MQTT 排空重叠，不按延迟下降推算扩容收益 |
| 故障与恢复 | 一台测试设备，各一条消息 | 约 0.98 秒观测到活动告警与 AI 开始；恢复后约 0.67 秒观测到 ONLINE 与 AI 取消（skipped） |
| 巡检 | 101,129 台，真实 Harness | 18.087 秒完成，报告明细总数一致；进度响应不再内联明细，浏览器验证分页 |
| 运维报告 | 同数据量，真实模型 | HTTP 200，19.502 秒；单次功能回归，未测供应商总配额 |

PDF 文件为 3,198,188 字节。独立并发下载每档 10 秒：

| 并发 | 成功下载 | HTTP 429 | 成功份/秒 | 请求 P95 ms | 管理探针 P95 ms |
| --- | --- | --- | --- | --- | --- |
| 1 | 3,068 | 0 | 306.8 | 5.3 | 87.2 |
| 4 | 8,752 | 0 | 875.0 | 6.3 | 56.7 |
| 16 | 7,531 | 128,876 | 752.7 | 8.5 | 81.1 |
| 64 | 1,686 | 189,193 | 168.5 | 9.0 | 1,212.1 |

这是本机回环网络、同一文件的缓存下载，不代表冷渲染或公网用户数。16/64 并发档不合格；P95 混有快拒绝，发压器未按 Retry-After 退避，不能把低延迟解释为健康。

完整性核对结果：

- 两档 MQTT 共 3,422 条唯一消息，排空后全部有原文、标准消息、完成标记和唯一 ClickHouse 遥测。
- MQTT、混合上报及故障/恢复共 **7,915 条原文、7,915 条标准消息、0 条未完成、ClickHouse 7,915 行且唯一 ID 7,915**。
- 指定 36 个历史标准消息 ID，将 65 条死信按 ID 合并后经原消费链重发；未完成降为 0，ClickHouse 行数和唯一 ID 均为 36。原死信保留，没有删除 DLQ 或重置 offset。
- 排空后 Kafka 各组 lag=0，inbox pending=0、corrupt=0，Broker dropped=0；最终 API 重启清零了进程计数器，不得跨重启做差分。

## 历史验证与剩余边界

修复轮记录的验证包括正式 Go 包测试、受影响包定向 race、真实 PostgreSQL 临时 schema 回归、现有 EMQX 断开回归、前端 115 项测试/构建、Bash 部署模拟冒烟和 promtool 规则校验。当时没有 `pwsh`，未实际执行 PowerShell 入口；这些结果不是本次文档整理重新执行的结果。

当时只读容量检查：3 个池为 64 的进程加 32 预留，224≤300；5 个进程为 352>300。只说明连接预算，不能换算为业务容量。单节点 RF=1、MergeTree、本地 MQTT 队列和未知模型额度不支持“最高集群容量已验证”，检查器输出 `clusterCapacityVerified=false`。

未重新完成大规模 MQTT 连接、专用协议极限、告警/知识/备份风暴、直播转码、多节点故障、磁盘写满和生产长稳。50 条/秒混合负载仅持续 90 秒；MQTT 100 条/秒确认超时和 PDF 高并发拒绝仍是该环境的边界。目标硬件按 [容量验收流程](DEVELOPMENT.md#目标环境验收) 重新测量。

测试结束时发压器停止，测试产品/规则/监听停用，临时用户及密钥撤销，告警恢复；数据库测试记录、巡检报告、备份与原死信保留供复查。临时脚本、二进制和日志已清理。以上是 2026-09-27 的状态，不描述当前运行环境。

解读时保留以下口径：`okQps` 是响应或 ACK 完成速率；`p95ms/p99ms` 可能包含失败请求；`durationSec` 含在途收尾；`metricsValid=false` 和采样空值表示未知，不能填 0。`storageLagEnd` 与全管道 `lagEnd` 分开；计数器重置前后不直接相减。207 看 accepted/rejected，429 计为限制，MCP 的 HTTP 200 仍需检查 `isError`。命令退出码 0 只说明工具执行完。

无效早期 MQTT 轮次与受前置过载影响的总览轮次未进入主阶梯；对应观测仍保留。最终业务完成以唯一 ID、`processed_at`、适用消息类型的 ClickHouse 遥测和告警状态核对，不能只看 lag 或 PARSED。
