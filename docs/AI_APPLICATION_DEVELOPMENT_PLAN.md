**消防 IoT 平台五项 AI 应用开发方案**

设计日期：2026-10-01，源码核对始于2026-09-30。本文面向后端、前端、测试和产品人员，确定数据可信度、告警策略实验台、监测连续性与接入依赖、演练与处置复盘、维护效果与投入决策五项开发范围。工程交付与协议变更验收不在本次范围。

本文是开发设计，不是实现清单或运行验收报告。下文新增表、API、工作流、参数和行为均为拟实施契约。现状依据本次源码只读核对；当前工作区已有值班模块在途代码，不能将其未验证接口视为已交付能力。实施时复核该模块最终契约，本文不要求覆盖、回滚或迁移其他任务的工作。

**一 共同架构和业务约定**

五项功能采用同一条链路：Vue 页面选择任务及范围，HTTP API 校验权限，业务服务形成固定事实，确定性算法计算结果，再由用户显式启动 Harness 解读。事实计算、人工记录和业务确认不依赖模型成功。分析不改写设备在线状态、部件状态、原始报文、标准消息或生产告警。

| 应用 | 确定性服务负责 | AI 负责 | 正式业务动作 |
| --- | --- | --- | --- |
| 数据可信度 | 完整性、时间质量、量程和序列指标 | 解释异常依据，提出核实步骤 | 人工核实发现和维护质量配置 |
| 告警策略实验台 | 隔离求值、状态模拟、行为差异和标签匹配 | 解释差异，提出候选草稿 | 人工确认候选与发布 |
| 监测连续性 | 时间区间、依赖集合、共同缺报关联 | 解释薄弱环节和检查顺序 | 人工确认资料及整改事项 |
| 演练与复盘 | 节点证据、时间、缺项和目标比较 | 整理复盘及整改建议 | 人工确认正式复盘与整改 |
| 维护与投入 | 有效时长、故障统计、成本和透明排序 | 解释变化，起草投入理由 | 人工验收、事项处理和投入决定 |

不部署本地模型、GPU 或独立向量数据库。对话与推理沿用现有模型管理和 Harness；需要知识时使用当前外部 HTTPS Embedding API 与 PostgreSQL + pgvector。完全断网时，结构化计算、记录、人工确认与模板导出仍可使用，AI 解读显示不可用。

五项业务 Agent 不混入聊天工作台，不获取规则发布、设备控制、shell、文件系统或任意 SQL 能力。知识分别绑定到工作流，启用时遵守首次调用前授权预检索及现有无匹配策略。

**二 共享任务和事实服务**

只为这五项新增可复用分析服务，不替换已有巡检、容量测试或值班模块的任务系统。建议业务实现放在 internal/analytics/，模块算法分别独立；新增模型、接口、数据库适配与 HTTP handler 仍遵循现有分层。

| 共享对象 | 必要字段和用途 |
| --- | --- |
| AnalysisRun | id、tenantId、kind、creator、显式设备集合、权限版本、起止区间、配置版本、算法版本、状态、阶段、实际处理数量、执行租约、检查点、错误和完成时间 |
| AnalysisSnapshot | 不可变版本、范围、数据截至时间、输入清单或分块哈希、各来源覆盖、水位或读取时点、初始状态质量、factsHash、统计和限制 |
| AnalysisEvidence | 来源种类、来源ID、deviceId、时间、资源版本、必要的事实摘要、权限类别、原始证据可用性 |
| AnalysisAIRevision | snapshotId、workflowId、模型、提示版本、生成状态、Run ID、结构化解读、证据引用、覆盖范围、错误 |
| AnalysisReview | 关联版本、确认或争议结果、说明、确认人、时间及更正关系 |

分析任务状态固定为 QUEUED、PREPARING、RUNNING、SUCCEEDED、PARTIAL、FAILED、CANCELLED。AI 状态单独保存：QUEUED、RUNNING、SUCCEEDED、FAILED、CANCELLED。事实完成但 AI 失败时，不将整个分析任务标为失败。

运行完成后输入与指标冻结。补到数据或修改配置后，重算产生新任务并关联原任务，不能覆盖历史结果。PARTIAL 必须列出缺失来源、受影响区间和不可计算指标，不能展示为完整通过。

任务由 PostgreSQL 持久化并领取租约；跨副本通过事务领取，检查点与对应输出批次共同提交。领取或接管产生递增leaseToken，提交事务同时校验token、租约有效期及任务可写状态。旧worker即使已完成计算，也不得在失去租约后提交；停止、接管和权限撤销使旧token失效。进程中断后只恢复幂等计算；AI外部调用若不能确认结果，不将其描述为成功。AI响应保存时再次校验快照版本、任务状态及当前权限。

初始保护配置采用每租户每应用最多一个运行中的事实任务，其余排队；计算 worker 默认每进程两个。每批读取量、最大范围、运行时限和队列长度按部署配置限制，这些是资源保护参数，不是吞吐验收结论。请求超限在运行前返回明确原因；运行中停止在检查点边界生效。

AI 每次绑定一份快照，重复点击复用同版本运行任务。默认一次任务只解读一次，不因每条遥测、告警或任务刷新自动调用模型。再次解读由用户触发并保存新版本。

数据库中的完整明细与模型读取样本分开。模型输入受现有 Harness 请求预算约束，先包含准确汇总，再选择重点证据；剩余证据经受控分页工具读取。正文标明 AI 实际覆盖范围，不能声称已审阅未提供的所有数据。输出验证结构、事实引用和对象范围，无法验证的模型结论不能成为确定性发现。

**事实查询契约**

新增批量读取端口：QueryMeasurementSeries、ListRawParseOutcomes、ListAlarmReportEvents、ListAlarmLifecycleEvents、ListDeviceStateIntervals、ListHandlingRecords、GetDependencySnapshot 和 GetConfigurationHistory。每个查询返回实际覆盖区间、完整性、游标及来源版本。

设备状态区间查询必须读取窗口开始前的最后一个可信状态，并获取窗口内全部转换。告警查询分别返回产生、再次上报、确认、恢复和关闭事件；不能套用按 last_triggered_at 筛选的当前告警列表还原过程，也不能用累计 TriggerCount 当作完整时间序列。

优先复用并完善已经存在或正在完善的持久业务事件及状态事件，不为五个应用复制五份事实账本。现有 outbox 用于可靠投递，不能将排空后删除的投递记录当成长期历史。缺少事务事件的状态变更需在原仓储事务中补齐对应记录，普通 best effort 审计只作补充线索。

事件至少保留 sourceEventId、source、actor、resourceId、resourceVersion、occurredAt 和 recordedAt，以来源唯一键去重。自动动作与人工动作分别记录。平台接收时间从可靠原文或接入记录读取，不能假定设备时间等于接收时间。

测量另保留availableAt，定义为该版本有效标准测量成功提交到平台可查询持久存储的时刻。eventAt是设备声明发生时间，receivedAt是平台收包时间，availableAt是该有效测量可被平台读取的时间。它们分别用于事件分析、接收连续性和实时有效数据连续性，不能相互替代。补充不可变的首次成功提交记录及阶段来源；最后ParseAttemptedAt会变化，不作首次可用时间。

读模型保存collectionStartedAt、backfillRange、backfillStatus、availableAtSource和historicalReconstructionQuality。旧数据可核实的processed_at仅按“标准消息处理完成”阶段作保守历史依据，并注明来源；缺少首次可用时间时显示未知，不能用receivedAt填充。源数据过期、回填未完成和现场确实未上报分别显示。开始采集前不存在的关系、规则版本或过程记录不能补造。

PostgreSQL 业务事实在一致性读取中生成快照；涉及 ClickHouse 的读取记录独立来源截止点及覆盖情况。不能以跨库查询开始时间宣称所有来源同时完整，也不能用预分配最大序号证明所有事务已经提交。数据不存在、过期、未获权限和查询失败分别表示。

**权限和资料访问**

租户从登录身份取值。所有创建、查询、标注、AI、确认、原文导航、附件和导出均验证操作权限及当前设备范围。任务的设备集合是发起时获授权集合的快照，发送模型前和工具调用时继续检查当前权限。

范围缩小后，包含越权设备的整份 AI 正文或报告不得仅删掉明细后继续展示。完整正文拒绝读取；需要局部结果时，按当前获授权集合另行生成。父设备与子设备分别授权，不返回未授权父设备ID、同组隐藏成员数或由总数差值推断的隐藏数据。

产品级、租户级共享配置的发布要求覆盖全部受影响设备及当前管理权限。普通用户可保存个人分析参数，但不能修改共享阈值。分析权限与规则发布权限分开；费用、报价、人员联系方式等另设读取权限，不把这些内容混入普通设备报告或模型输入。

**三 数据可信度分析**

目标是发现可核对的数据质量问题，并给出待核实线索。结果分为有质量问题、待核实、不适用和证据不足；它不是消防风险分，也不判断传感器已经损坏。

当前属性历史有 timestamp、value、messageId，物模型有类型和单位，原文有解析、协议及点表版本。缺少统一量程、预期上报、精度、工况及校准记录。当前 LastSeenAt 来自消息时间，分析必须另外读取平台接收时间。原文 Parsed 是 API 填充信息，不能把 false 全部认定为解析失败；归档、未尝试解析、最后解析失败和成功标准消息需分别统计。

**用户流程和页面**

设备详情增加“数据质量”标签，管理侧设置“数据质量”入口。用户先确认产品或测点的上报模式和物理信息，再选设备、属性、区间及配置版本运行分析。概览分别展示各质量维度、无法评估对象和资料缺口；明细按产品、属性、问题类型和人工核实状态过滤。

发现详情展示原值曲线、基线、阈值、设备时间与接收时间、代表报文和协议版本。人工可标记已确认问题、存在正常解释、已处理或继续观察，并填写依据。这些标记不更改原始数据或业务告警。

| 新增对象 | 核心字段 |
| --- | --- |
| QualityProfile | 产品或设备、属性、版本、periodic或event模式、scheduleAnchor、effectiveFrom、周期与容忍、类型与单位、量程、精度epsilon、变化率、窗口、最小样本、基线要求 |
| QualityBaseline | 起止、工况、协议及配置版本、样本数、中位数、MAD、分位值、确认人、有效期 |
| QualityWindowMetric | 设备、属性、窗口、分母、期望槽数、覆盖槽数、有效样本、重复、乱序、越界、时间异常、统计值、完整性 |
| QualityFinding | 类型、区间、阈值、指标引用、提示等级、证据、人工核实状态及说明 |
| CalibrationRecord | 设备或测点、校准日期、依据、量程及精度变化、实施人、附件 |

保留历史配置版本；一个窗口跨越单位、协议或精度变化时分段分析。原始时序仍使用现有 PostgreSQL / ClickHouse，新增汇总及少量证据，不复制整份时序库。源记录过期时保留已冻结指标，并显示原文证据已过期。

**算法契约**

1. 格式检查采用物模型类型、必填要求及有限数值校验。仅在单位及量程已确认后判定越界；未配置时显示未评估。
2. 周期完整性采用固定scheduleAnchor和配置生效时间建立期望槽，不随查询起点重新定相位。容忍量必须小于半周期，避免槽区间重叠；配置超出时拒绝保存。一条样本只能覆盖一个最近槽，距离相等时选较早槽，同槽多条保留距槽中心最近者，同距按receivedAt、messageId稳定排序。边界读取增加容忍padding，只统计中心落在[start,end)内的槽。缺报比例为缺失槽数除以应有槽数，分母为零显示不适用。事件驱动测点不计算周期缺报率，心跳另行评价。
3. 接收连续性以平台接收时间计算，补报只证明历史数据存在，不能填补过去实时监测的缺口。设备事件时间曲线单独显示。
4. 时间质量统计乱序、时间回退、异常未来时间及接收时间减设备时间。时间差不是精确单向网络延迟，设备时钟未校准时必须说明。
5. 长期无变化要求连续有效样本跨越配置时长，变化范围小于epsilon；布尔和状态属性按允许稳定时长处理。正常恒定工况和量化精度可作为人工解释。
6. 变化率使用相邻有效样本的绝对值差除以时间差；相同时间、长缺口、换版本边界不作直接比较。
7. 历史偏离只比较同单位、同工况和同协议版本的足量基线，采用中位数、MAD或分位范围。MAD为零时采用已配置的精度或绝对偏差门槛，缺少可用门槛则不判定。
8. 小幅漂移可采用基线已确认后的CUSUM，参数版本与基线绑定；基线未确认时不自动判定。此方法用于变化线索，不证明物理故障，方法依据见 [NIST CUSUM说明](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc323.htm)。
9. 接入和解析质量分别统计归档、尝试解析、最后失败及成功标准消息。若需要每次解析尝试的失败比例，新增不可变尝试记录，不能由最后结果反推。

周期、量程和epsilon没有通用默认值，必须由产品资料或现场确认。统计比较的软件最小样本保护下限初始为30，可提高；达到下限不代表已充分验证统计有效性。初版不提供合成可信度总分，直接展示各维度、分母和未知项。

**接口和工作流**

API统一以 /api/v1/data-quality 为前缀：profiles用于配置及版本发布，baselines用于基线确认，calibrations用于校准记录，POST runs创建任务，GET runs/:id及其metrics、findings、evidence读取结果，POST runs/:id/stop停止，POST findings/:id/reviews记录核实，POST runs/:id/ai-jobs显式解读，GET runs/:id/export导出。

Harness工作流为 data-quality-analyst，仅允许读取绑定快照的指标、发现、证据及受权知识。输出summary、interpretations、suggestedVerification、limitations，每项解释引用factIds。模型不能改数值、阈值、标签或设备状态，也不能创建消防告警。

**开发顺序和验收**

先做配置及受权批量查询，再实现窗口算法和证据页，随后补人工反馈，最后接AI。受控序列验证缺槽、同槽重复、补报、时间异常、倍率突变、正常稳定、混合类型、单位和版本变化。切换查询起点不能改变完整槽的匹配结果，边界样本与超半周期容忍配置单独回归。PostgreSQL与ClickHouse对同一序列得出一致结果，查询裁剪明确PARTIAL。还需用实际正常运行数据核对误提示，验证源证据过期、回填未完成、权限撤销、AI失败和窄屏曲线。

**四 告警策略实验台**

目标是在固定历史输入上比较当前与候选规则行为，形成可审阅的修改依据。无真实标签时只报告行为差异；有覆盖充分的真实事件与负例标签后，才能讨论检出和误报。

当前规则有条件、表达式、DurationSeconds、恢复条件、动作、启用和Version，但保存会覆盖当前正文，没有完整不可变历史。现有DRY_RUN和DIFF只处理解析结果，REINGEST进入生产链路，均不充当规则回测入口。

**使用流程与隔离架构**

入口设在告警规则的“实验”页签。依次选择基线规则集、编辑一份候选、固定数据集、运行比较、核对差异与标签、确认实验结论、通过现有受权发布路径应用候选。

新增 internal/rulelab/。从当前实现提取可共用的纯条件求值和状态转换，输入标准消息、规则快照、分支状态和虚拟时钟，输出判定、状态变化及意向动作。生产执行器执行真实副作用，实验执行器只写实验表。共享逻辑的提取必须用现有生产回归保护，不顺带修改规则业务语义。

实验器不持有生产Bus、Realtime、设备控制或告警写仓储。基线和候选各有持续条件pending、活动告警、消息幂等及恢复状态。相同数据、时序、时钟和语义版本作用于两分支。候选只替换选定规则，其他规则保持一致。

设备主动ALARM_REPORT的原始断言始终保留，模拟沿用当前ruleAlarmHandled及部件路由：规则已成功处理时采用规则告警，未处理时走direct回退，部件按部件链路处理，不额外重复创建direct告警。分别统计设备断言、规则告警周期及部件告警；重新归类不能被算作丢失断言。实验中的意向动作数不是实际通知送达数。

**数据和时间语义**

默认输入已保存的StandardMessage，固定rawMessageId、解析版本、物模型及单位，避免调整规则时同时改变解析。输入清单或分块快照不可变，不能边读取变化中的表边累计结果。

| 新增对象 | 核心字段 |
| --- | --- |
| AlarmRuleRevision与Activation | 不可变正文、版本、哈希、变更原因、生效区间、发布人与回滚来源 |
| RuleEvaluationTrace | 标准消息、claim/attempt身份、实际规则版本、逐规则逐阶段求值时钟、提交结果、规则集哈希、语义版本、初态来源 |
| RuleLabDataset及Chunk | 明确设备集合、主区间、预热区间、输入哈希、各时间字段、覆盖、初态质量 |
| RuleLabExperiment | 数据集、基线与候选、行为假设、事件匹配条件、标签版本 |
| RuleLabOutcome | 分支、逻辑告警周期、触发恢复时间、意向动作和证据 |
| RuleLabLabel | 设备、事件类型、起止区间、核实结论、依据、审核人与版本 |
| RuleLabReport | 固定统计、共同及独有事件、限制、AI解释与人工结论 |

当前持续条件采用处理时钟，首次匹配建立pending，后续匹配消息到来才检查持续时间；不匹配会清除pending。它不是到时自动触发。实验必须保持该语义，不把事件时间排序结果包装成生产重现。

生产目前可能在同一消息的持续判断、产生和恢复阶段多次读取时钟。trace须按规则及阶段记录实际版本、时刻、claim/attempt、成功提交或部分失败重试身份；只有输入顺序、各阶段时钟、版本和必要状态均完整时，才标为精确语义重现。若将生产改为每消息单一时钟，需要另登记语义版本并验证影响。旧数据只有StandardMessage时，公开采用的历史排序、时钟和预热假设，报告标为历史模拟。当前版本登记为初始版本，不能补造过去规则生效历史。

两分支分别按自身规则运行同一预热数据。缺少窗口起点状态、完整恢复边界或充分预热时，相关结果显示不确定，不能将基线pending复制给修改了条件的候选。人工确认、关闭单独作为事件；无法映射的旧人工动作不自动施加到候选新告警。

把触发优先、恢复匹配、ACTIVE与ACKED处理、重复消息和意向动作等当前行为记录成语义版本。本次所查规则自动恢复仅处理ACTIVE；ACKED恢复不能仅在实验器扩大。发现业务契约与现实现不一致时，单独完成相关修复与回归，再用于两分支；不能只在实验器修正，从而使实验结果无法指导生产。

**指标和标签**

无真实标签时计算匹配消息、新告警周期、重复上报、持续及未恢复、恢复后再触发、基线独有和候选独有、共同事件的相对触发时间、意向动作、错误与数据覆盖。不能据此显示准确率提升或误报下降。

标签分为CONFIRMED_EVENT、TEST、NO_ABNORMALITY_FOUND、UNKNOWN，关联事件区间，不只关联已出现的告警。UNKNOWN不作为负例；仅标注已触发告警不能计算总体召回率。负例须有明确范围及核实依据。

有代表性正负区间后，在运行前冻结共同可评价集合：设备、事件类型、已核实正负区间及统一排除区间，两分支不能分别排除困难样本。按固定时间容差建立允许匹配对，采用确定的一对一最大匹配，同样匹配数时优先总时间误差最小，再按稳定ID排序。TP为匹配对数，precision=TP/该分支共同评价范围内的全部告警周期，recall=TP/同一范围内的全部真实事件。多个独立告警周期对应同一真实事件时只有一个增加TP，其余按预先固定政策计为额外提醒，不能临时合并以提高precision。聚合策略在运行前固定，重复报文不增加告警周期。分母为零显示不适用。排除缺测和未知初态后只称“可评价区间召回率”，不代表全系统召回率。

调参区间与最终留出评价区间分开；重用留出区间须记录，不能把调参后的结果称为独立验证。

**页面、API和AI**

结果页顶部先显示范围、数据覆盖、初态和语义质量，再展示并排指标、差异事件、字段曲线、原文和标签。候选编辑不改变当前生效规则。数据不足、未匹配人工动作及错误样本不隐藏。

Harness工作流 rule-policy-analyst只读取固定实验汇总、样例、证据和标签。候选由模型返回结构化草稿，平台调用已有规则校验，保存禁用候选；不授予模型发布或启用工具，也不自动发起无限调参。

正式发布检查expectedBaselineVersion、候选校验和实验引用，并记录发布原因；基线已变化返回409。新增版本及生效记录与当前指针在同一事务保存。候选先存禁用版本，发布使用现有管理权限。

规则版本切换采用以下固定政策：pending键增加ruleRevision，新版本从发布后的首条新消息重新计时，旧pending不继承或复活；已有活动告警保留createdRuleRevision，新上报另存triggerRuleRevision。沿用tenant/device/rule_id活动唯一身份，未解除期间新版本匹配可以更新同一告警，但不能覆盖其产生版本或另造活动实例。恢复优先依据该活动告警产生版本的Recovery；没有配置自动恢复的告警继续走现有人工或设备恢复流程。旧版本保留到关联生命周期完结，规则禁用或删除不静默清除未解除告警。恢复与触发同报文的次序沿语义版本执行，已解除后新消息才创建新的周期。ACKED处理先保持生产语义；若需修复，作为独立语义版本同步修改生产和实验。规则生效历史和必要求值语义是本模块新增范围；协议发布、现场验收不在范围。

**开发顺序和验收**

先补规则历史与固定数据集，再提取共享纯求值并验证零差异，随后完成双分支、初态、人工标签和页面，最后接AI及发布记录。核心回归包含持续条件临界点、不匹配清零、断档、触发恢复同时成立、ACTIVE/ACKED语义、重复消息、主动设备与部件告警、缺字段和表达式错误。实验期间生产告警、状态、队列、通知及联动写入必须为零。验证重启检查点、发布冲突、权限撤销、无标签、无模型和初态不足。

**五 监测连续性与接入依赖分析**

目标是发现数据中断、集中接入依赖及可见设备影响范围。它只评价平台监测连续性，不判断消防设施合规数量、物理覆盖、水力能力或事故概率，也不恢复独立孪生拓扑和设备影子。

现有主子设备、GatewayID、ConnectorProfileID及CollectorID可以作为依赖来源。状态历史有基础，但完整区间、起点状态和历史关系需要补齐。当前工作区的值班事件记录只可作为待验证复用来源，不能代替本模块验收。

**计算口径**

周期测点分别建立接收区间与有效数据区间。接收区间使用receivedAt；有效数据区间从该属性实际availableAt起算，并要求其源样本仍符合时效策略，期限根据预期周期与容忍确定。排队半小时才可读取的测量不能从半小时前收包时刻起算有效，旧报文次日重放也不能美化过去实时监测。过期样本即使解析成功，也不刷新当前有效期。按区间并集计算可用、缺口、最长缺口和次数。数据可信度结果按固定版本消费，保留接收时间、设备时间和可用时间的不同口径。

只有配置允许的messageType、包含对应关键属性且类型有效的报文才能刷新该属性有效期。心跳、日志、告警或其他字段上报不能自动刷新压力等缺失测点，父网关消息不能刷新子设备。逐属性计算后再按Profile中固定ALL/ANY合并，页面展示策略及各属性缺口。availableAt或历史有效期依据无法重建时，相关数据区间标为未知，不能判为现场缺报或可用。

连接状态区间以窗口前可信状态为起点，按全部转换重建。缺少起点或存在事件缺失时标为未知。连接保持但没有有效报文、原文存在但解析失败、父设备在线但子设备静默分别展示。

同时展示：已知可用时长、已知不可用时长、未知时长及总计划观察时长。已知区间可用率=已知可用/(已知可用+已知不可用)，并展示已知区间覆盖率。完整窗口可用率只有未知时长为零时才给出，避免排除未知后显示虚假的高可用。

接入组集中比例为组内可见设备数/本次已授权分析设备数，不显示完整隐藏成员数。分组说明接入关系，不直接认定网络、电源或物理设施单点故障。事件上报设备不计算未知固定周期下的数据可用率。

共同缺报以区间重叠或Jaccard计算，门槛、时间粒度与最少事件数由配置确定。相似性只表示重叠现象，不自动判为共同原因。假设影响计算只采用该快照的接入成员，不发明备用线路或冗余能力。

历史依赖变化按有效区间分段，当前关系不能重写过去影响范围。上线前缺少历史关系时，仅支持当前快照假设，历史依赖结论明确未覆盖。

**六 演练与处置流程复盘**

目标是管理计划、过程证据、正式复盘及整改。演练和真实事件可以共用复盘计算，但执行来源明确区分。本模块不控制设备、不代替应急指挥，不根据平台点击推断现场动作。

| --- | --- |
| ResponseProcedureRevision | 适用场景、步骤ID、责任角色、前置步骤、规定证据、计时起点、单位设定目标、版本 |
| DrillPlan | 场景、岗位、设备范围、人员、计划时间、流程版本、状态 |

演练计划采用DRAFT、PUBLISHED、RUNNING、ENDED、REVIEWED、ARCHIVED及CANCELLED。真实案例从获授权告警人工建立，采用RECORDING、ENDED、REVIEWED、ARCHIVED，创建案例不改变告警状态。节点证据采用UNVERIFIED、CONFIRMED、DISPUTED。

主管发布流程版本并编制计划，开始时冻结流程和人员；系统记录能够证明的操作节点，人员补充通知、到场、检查和反馈；结束后计算事实，负责人选择AI复盘或手工编写，确认正式版本，再将选定建议创建为整改事项。结束或归档不自动完成整改。

**模拟与生产数据隔离**

模拟事件只写演练记录，不进入RawMessage、Parser或生产Alarm链路，不能使用REINGEST模拟演练。真实设备上报不因处于演练时间窗被自动改为演练；真实ALARM_REPORT继续完整处理、展示和通知。

演练可以引用具体生产记录作为证据，但不能修改其来源或状态。测试关联按明确报文或单次上报证据保存，不给整台设备、整段时间或聚合告警整体排除标签。存在混入真实事件的可能时，保留生产或未分类状态。

资料关联中的PRODUCTION、EXERCISE、TEST、UNCLASSIFIED由服务端依据可信来源和审核确定，普通请求体不能用标签绕过生产处理。人工现场试验在生产链路中的真实报警仍正常通知。分析统计排除经过确认的测试样本时，保存排除清单和理由，不能删除业务事实。

**节点计算与AI**

平台确认耗时从可靠平台接收时间到服务端告警确认时间；通知、现场到达和反馈使用流程定义的起点与明确节点。ACK仅证明平台操作，没有到场记录时显示未记录，不声称人员没有执行。

必要节点完成率=具备规定证据的已确认必要节点/本次必要节点；证据覆盖率=有效规定证据/应有证据。这些是记录与流程指标，不代表事故处置安全程度。时钟冲突导致负时长时显示时间异常，不能修成零；未完成节点展示等待时长。

流程目标由单位设置并版本化，不自动声称为法规时限。评估流程按“目标、关键任务、证据、结果、整改”组织，可参考 [FEMA演练评估指南](https://preptoolkit.fema.gov/web/hseep-resources/eegs)，不将国外材料用作本项目消防合规标准。

确认后的复盘版本冻结。补登记节点、迟到事件或争议更正提示新证据，重新计算或AI复盘产生新版本，并保留替代关系。AI工作流 response-reviewer仅读取固定流程、节点、计算结果和受权资料，输出过程摘要、观察到的卡点、证据缺口和整改建议。人工确认后才建立正式整改，模型不填造现场节点或给出自主应急指令。

目标是保存实物资产、维修干预和验收，比较可解释的维护前后变化，再辅助负责人形成投入清单。模块不预测精确剩余寿命、不自动证明维修因果效果、不执行采购。

**资产和记录**

| 新增对象 | 核心字段 |
| --- | --- |
| AssetInstance | 平台设备或部件、实物标识、制造/安装/投运/退役日期、依据、重要性、实例有效区间 |
| MaintenanceIntervention | 资产、影响范围、类型、起止、原因、已采取动作、人员、配件、关联故障和事项、状态 |
| MaintenanceVerification | 规定验收项、实际结果、验收人、时间、证据、PENDING/PASSED/FAILED/UNKNOWN |
| OperatingContext | 工况区间、运行强度、停运、测试、施工、规则/协议/网关/上报周期变更与依据 |
| MaintenanceObservationRevision | SAME_INSTANCE_REPAIR或CROSS_INSTANCE_REPLACEMENT、beforeAssetId/afterAssetId、切换时间、前后窗口、固定输入、有效时长、状态覆盖、排除区间、指标、混杂、准入参数、解释和人工核实 |
| MaintenanceCost | ESTIMATE或ACTUAL、分项金额、币种、发生或报价日期、规划范围、来源及读取权限 |
| InvestmentScenario | 预算、币种、规划期、候选动作、报价、排序策略版本、人工调整、决定及原因 |

ManagedDevice.CreatedAt只代表平台注册日期，不能填投运年限。更换实物但沿用同一平台设备ID时，结束旧AssetInstance并建立新实例。部件级资产必须有稳定部件关联；只有自由文本位置时不虚构实例身份。

同实例维修的beforeAssetId与afterAssetId相同；跨实例替换分别绑定旧资产和新资产及实际切换时间。前窗口与旧实例投运期求交，后窗口与新实例投运期求交，设备ID相同不能消除实物边界。平台事件必须按事件时间及实例有效区间归属；资产边界有争议时不输出跨实例比较。

维修记录采用DRAFT、IN_PROGRESS、COMPLETED、CANCELLED。COMPLETED表示工作记录结束，功能验收独立。观察采用PLANNED、OBSERVING、READY、REVIEWED及INSUFFICIENT、CONFOUNDED。投入方案采用DRAFT、REVIEWED、DECIDED、ARCHIVED；DECIDED不表示采购完成。

**前后变化观察**

用户从故障或事项创建维修记录，补实际动作和成本，再登记功能验收，选择前后区间及工况，形成变化观察。重新在线只是系统证据之一，不能代替功能验收。

有效观察时长按小时计算：先取观察窗口与实物投运期的交集，再扣除有依据的计划停运、已确认测试和平台观测不可用区间的并集，防止重叠扣除。设备自身离线属于结果指标，不能从分母扣除。设备没有报文也不能自行认定平台观测不可用。

确认故障率=已确认故障周期数/有效观察小时×1000，单位为次/1000小时；仅在故障事件来源完整性达到所选准入要求时给出，未知故障来源区间单列。观测覆盖率=有效观察小时/对应侧窗口与投运期交集小时。

离线指标另用状态可确认区间：T状态=有效窗口内已确认在线小时+已确认离线小时；已知区间离线比例=已确认离线小时/T状态，状态覆盖率=T状态/有效观察小时。完整窗口离线比例仅在状态未知小时为零时给出。状态未知不当作在线，也不能通过扩大分母稀释离线比例。例如10小时中9小时未知、1小时离线，展示已知区间离线100%、状态覆盖10%，不能只显示离线10%。设备自身离线始终留在有效分母中。各项同时显示数量、时长、未知及排除原因，分母为零显示不适用。

故障按核实后的同类故障周期去重；聚合告警条数、重复上报、真实火警和测试不能混作维修故障次数。窗口起点状态缺失或观测缺口无法解释时，相关区间显示未知，不补成在线或零故障。

还展示同类问题再次出现时间、功能验收、重复维修、已记录成本和数据质量变化。零故障窗口不能直接声称故障率已降低到零风险；前后观测时长不同必须使用标准化指标。

准入参数按产品或故障类型设置最低有效小时、最低覆盖、确认样本要求、维修后等待期和工况可比性。未配置比较要求时先展示描述性指标，不自动输出有效性结论。门槛仅允许描述性比较，不证明统计显著或因果关系。

规则、协议、网关、测点、上报周期或运行强度同时变化时标为混杂。AI只能写观察到的变化及限制，不能把故障减少归因于维修。原始输入不足、分母为零、关键工况未知时显示证据不足。优先级方法可参考 [DOE故障诊断与优先级研究](https://www.energy.gov/cmei/buildings/articles/fault-detection-and-diagnostics-test-datasets-and-prioritization-methods)，建筑能耗研究不能直接证明消防维护收益。

**成本和投入排序**

金额使用精确十进制，保存币种、估算/实际、来源日期和时间范围。未知费用不填零。材料、人工和外部服务分项记录；工时不默认折算金额。第一版一个方案只用单一币种，没有可靠汇率日期时不合计多币种。

历史维护支出与未来报价分开，一次性更换成本与规划期持续维护成本采用相同规划范围。缺少后续维护费用时不自动声称全生命周期成本更低，也不生成无依据ROI。

采用优先级分层和层内透明排序。默认固定顺序为：单位人工确认的必需事项分层，层内按未解除且已核实功能缺陷、人工重要性等级、同口径确认故障率、已知离线小时排序，最后按稳定资产ID打破同值。工况或数据覆盖不满足比较要求的指标不参加数值排序，放入同层待补资料区，不视为低风险。成本、年限和执行条件作为可见约束，不在默认策略中偷偷加权；自定义策略必须保存权重、方向、缺失处理和每项贡献。

预算清单按已确认优先顺序逐项累计有效报价，达到预算边界时区分已纳入、待追加预算和报价缺失。必需事项超预算时明确显示缺口，由人员决定，不自动降级。此清单是可解释排序及预算试算，不声称求得最优采购组合。人工调整、替换动作和例外均保存理由。

AI可以提出继续观察、进一步检查、维修或评估更换，并解释已有因素，不能发明维修收益、设备故障概率或更换后的改善量。维修和投入的资金信息按独立权限提供，生成包含资金的AI报告也必须绑定该权限。

使用受限费用的排序、推荐动作、理由、快照和AI正文全部继承资金权限；仅隐藏金额不足以消除衍生泄露。权限撤销后拒绝读取旧资金版本，需要普通版本则按不含资金因素的输入重新计算，不只删除金额字段。

**页面、接口和工作流**

“维护与投入”包含资产、维修、变化观察和投入方案。观察页并列前后窗口、有效时长、指标、排除原因和混杂，不用单一绿色“维修有效”标签替代证据。投入表直接展示优先理由、费用依据、未知数据和人工调整。

接口为 /api/v1/assets，/api/v1/maintenance-records及actions、verifications、observations；/api/v1/maintenance-observations/:id读取，ai-jobs解读；/api/v1/investment-scenarios管理方案，evaluate执行透明排序，ai-jobs整理投入说明，decisions记录人工决定。

Harness工作流 maintenance-outcome-reviewer负责变化解释，maintenance-investment-advisor负责投入理由。两者只读取固定获授权事实；资金工具单独授权。模型不能登记费用、通过功能验收、完成事项或确认采购。

维修关联值班或整改事项时，事项完成由有权限人员依据验收确认，不能由维修记录COMPLETED自动代替。即使尚未启用值班模块，也可从设备建立维修记录，本模块不被在途值班实现阻塞。

**开发顺序和验收**

先补实物实例和维修验收，再补工况及区间查询、标准化指标，随后做投入方案，最后接AI。验证平台注册日期未知年限、沿用设备ID更换实物的两侧资产绑定、短观察期、状态未知分母、重叠排除、缺测、测试混入、工况变化、未知费用、多币种及排序缺失资料。测试无资金权限和撤权后的历史排序及AI正文。对手算小样例核对所有分母和优先理由，AI失败时仍能完成业务记录与人工决定。

**八 接口通则和工程落点**

所有新分析接口采用当前错误响应和权限目录机制。创建任务返回202及持久任务ID；分页结果默认20、最多100，并返回total及明确完整性。所有写操作验证关联资源所属租户、设备范围和expectedVersion。正式确认与发布使用幂等键；冲突返回409。

接口中不得接收任意上游URL或任意SQL。时间保存UTC时间戳，界面使用配置时区，区间统一[start,end)。报告直接保存固定指标，下载不重新运行分析。原文链接使用rawMessageId，标准消息ID仅作关联。
