# 值班管理与 AI 交接助手

[使用流程](#使用流程) · [状态与事实](#状态与事实) · [权限](#权限) · [AI 与任务](#ai-与后台任务) · [API](#api-与存储) · [运行与备份](#运行与备份)

平台入口为“值班管理”，包含我的值班、排班日历、交接记录、跟进事项、业务主事项与设置。排班、实际到岗、正式交接与持续跟进使用独立记录；AI 只整理人工可复核的交接草稿。内网中的排班与人工交接不依赖模型连接，AI 沿用外部 API 与 Harness，不增加本地模型部署。

## 使用流程

1. 在现有用户管理中建立值班账号，授予值班菜单、相应操作及完整岗位设备范围。排班不会扩大用户权限。
2. 在设置中配置岗位、主管、负责设备、最低到岗人数和提醒时间；建立班组及跨午夜班次模板。同一设备不得同时归属多个岗位。
3. 创建排班或按日期区间批量生成，检查时长、岗位重叠、人员冲突、账号资格与覆盖缺口后发布。已发布计划调整需要原因，保留历史；取消保留记录。CSV 先预览再携带摘要导入，不能跳过预览校验或重复导入同一来源。
4. 人员先记录到岗；到岗不自动取得值班责任。首次开班由主管或管理员确认，负责人已到岗且满足人数要求后开启实际班次。后续通过正式交接开启下一班。
5. 当班人员填写人工记录、上传附件，创建跟进事项。错误记录通过更正追加，原记录保留。代班、负责人替换和异常结束需要原因，重新校验人员权限及跨岗位实际值守冲突。
6. 交班负责人选择下一次已发布排班，生成冻结事实版本，填写人工说明；可以显式点击“AI 整理交接”。核对设备状态、活动告警、当班事件、人工记录及未完成事项，再提交。
7. 接班负责人先到岗，核对精确版本和草稿后新增变化，再确认接收。接收事务同时结束旧班、开启新班、保存接收事实版本并接续未完成事项。未接收时旧班继续承担责任，不按排班时钟自动切换。
8. 交接后追加说明或晚到事件作为补充保留，原签署版本不被覆盖。历史可以选择固定版本阅读、下载 PDF 或导出全部事件 CSV。

“业务主事项”读取当前获授权的整改与维修主记录，主责、状态和功能验收来自主对象。可在实际 ACTIVE 班次建立当班跟进；当班事项完成不代替整改或维修验收，详细业务见 [演练与复盘](ANALYTICS.md#演练与复盘) 和 [设备维护](ANALYTICS.md#维护与投入)。

## 状态与事实

| 对象 | 状态与边界 |
| --- | --- |
| 排班 | DRAFT、PUBLISHED、CANCELLED；计划与实际班次独立 |
| 实际班次 | 到岗准备与 ACTIVE、ENDED；同一岗位最多一个 ACTIVE |
| 交接 | DRAFT、SUBMITTED、RETURNED、ACCEPTED、VOID；退回后产生新事实版本，历次确认记录保留 |
| 跟进事项 | OPEN、IN_PROGRESS、PENDING_VERIFICATION、DONE、CANCELLED；完成须有结果，取消须有原因，与告警状态独立 |
| AI 任务 | QUEUED、RUNNING、STOP_REQUESTED、SUCCEEDED、FAILED、CANCELLED、INTERRUPTED；失败不阻止人工交接 |

每个文档带租户、版本、创建及更新时间。更新使用 `expectedVersion`；正式动作使用 `idempotencyKey`，同键不同请求冲突，网络不确定时原请求原键重试。正文范围变更后重新校验资格，不能借幂等回执绕过撤权。

`duty_business_event` 与告警、设备状态事实在同一数据库事务提交，覆盖创建、再次上报、确认、恢复、关闭、连接变化与离线状态。普通审计日志不是交接统计的数据来源。事件保留发生时间与记录时间，时间过滤采用毫秒半开区间 `[start,end)`；冻结版本采用截止毫秒的下一毫秒作为 `end`。旧系统升级前没有写入本台账的历史事件不会被补造。

版本保留完整事件、人工记录、事项、设备状态及活动告警快照。完整事件与 AI 输入分别处理，超过 2000 条事件仍完整冻结和导出。已知事件 ID 用于识别长事务晚提交，不把最大数据库序号当成提交水位。当前状态变化后再恢复到原状态仍属于需要核对的增量。

交班签署引用提交版本；接班另存当时完整事实及确认摘要。签收事务对旧班、下一班、事项、确认和幂等回执统一提交。晚到事件由持久后台扫描识别，补到已签交接的独立附录并提醒当前负责人。

## 权限

菜单为 `menu:duty`，操作为 `action:duty:<名称>`：

| 名称 | 用途 |
| --- | --- |
| settings | 岗位、班组及模板管理 |
| roster | 生成、导入、调整、发布及取消排班；首次开班另检查主管资格 |
| participate | 到岗、接班准备、代班 |
| record | 填写、更正和上传值班记录附件 |
| handover | 创建、编辑、提交、作废和追加交班说明 |
| accept | 接收或退回交接，另检查下一班负责人资格 |
| ai | 显式整理、停止 AI 任务 |
| item | 事项创建、进展、转交、完成及取消 |
| history | 阅读获授权岗位的历史资料 |
| export | 下载固定版本 PDF 与完整事件 CSV |

所有 API、附件和模型工具都校验租户和当前设备范围。普通用户还须有相应岗位参与资格；当前值班成员可查看本岗位后续已发布排班以选择交接对象。完整记录和报告继承整个实际班次范围，不能通过只关联一个获授权设备绕过其余设备的范围校验。范围缩小导致整份旧报告超权时，整份拒绝读取。主管资格、岗位范围及参与资格均由服务端校验。

## AI 与后台任务

工作流 ID 为 `duty-handover`，是不可编辑的内置业务 Agent，不出现在普通聊天 Agent 中。所有调用经 Harness，工具只有 `query_duty_snapshot` 和按授权启用的 `query_knowledge_base`；无设备控制、规则发布、shell、文件系统或任意 SQL。

推理身份绑定发起人、会话与权限版本、任务、不可变交接版本及租约所有者。模型调用前、工具读取时和结果写回前重新核验。权限变化、版本变化或租约接管使旧运行失效；工具不接受调用者指定的其他任务、版本或设备参数。

默认按证据时间优先选择最近 100 条，允许请求最多 300 条，但证据 JSON 受 18 KiB 预算约束；输出明确实际覆盖数量。事件正文只向模型提供允许的业务字段，不默认发送完整报文、附件或凭据；人工文本手机号及明显凭据模式脱敏，包括 JSON/YAML 带引号的凭据。结果必须为结构化 JSON，说明和建议必须引用本次输入中的证据，平台校验引用，覆盖声明由服务端生成。事实统计不会由模型重算。AI 内容仍需人工复核。

交接详情显示持久 AI 任务状态、实际阶段和输入覆盖量；离开后重新打开按服务器任务继续读取进度。AI 成功后原子生成新的草稿版本，保留人工说明；若用户已经改版或提交，旧任务结果不覆盖正文。停止为持久状态，进程退出后过期租约可恢复；旧租约不能读取快照或写入结果。`STOP_REQUESTED` 的过期任务转为取消，不重新调用模型。

管理 API 进程运行后台扫描，每进程最多两个值班 AI 执行任务；共享 PostgreSQL 协调副本。提醒与 AI 独立，扫描产生临近交班、排班缺口、空岗、迟到接班、事项到期和晚到事件提醒；通知同事务持久化，已读按本人保存。任何提醒都不会自动启动模型。

知识默认关闭。需要 SOP 时在现有知识库页绑定到 `duty-handover` 并配置检索策略，发起人还须有知识库权限且显式选择使用知识。检索沿用当前外部 Embedding 与 PostgreSQL + pgvector。

## API 与存储

接口前缀 `/api/v1/duty`。列表支持 `page/pageSize` 或 `limit/offset`，服务端分页上限 100。写请求外层为 `{expectedVersion,idempotencyKey,body}`，租户、用户和资源类型由登录身份及路由确定。

| 接口 | 用途 |
| --- | --- |
| stations、teams、shift-templates | 配置增删改查；被历史业务引用的配置不能删除 |
| rosters、rosters/generate、rosters/import-preview、rosters/import | 排班与导入；`:id/validate`、publish、cancel 对应显式动作 |
| runs/current、runs/arrive、runs/open | 当前班次、到岗与首次开班；`:id/substitute`、end 管理代班及异常结束 |
| records、runs/:id/records、records/:id/correct | 人工记录与追加更正 |
| runs/:id/attachments、attachments/:id | multipart `file` 上传及经授权下载 |
| handovers、handovers/:id/revisions、handovers/:id/delta | 交接、版本与最新增量；submit、return、accept、void、amend 为业务动作 |
| handovers/:id/start-ai、ai-jobs、ai-jobs/:id/stop | 显式启动、查询与停止整理 |
| items、items/:id/events | 事项与历史；assign/transfer、status、complete、cancel 管理进展 |
| revisions/:id/events、events.csv、pdf | 固定版本完整事件分页、CSV 及 PDF |
| notifications、notifications/:id/read、options、events | 站内提醒、可选人员/设备与获授权事件 |

业务主事项目录另使用 `GET /api/v1/follow-up-sources`，按整改/维修的来源菜单、当前完整设备范围过滤后分页计数。

PostgreSQL 使用独立 `duty_*` 表，多副本共享持久事务、任务领取及后台租户枚举；ClickHouse 遥测层和 Redis 缓存层透传此契约，冻结快照在底层事务内读取。业务代码在 `internal/duty/`，HTTP 为 `internal/httpapi/duty*.go` 和 `follow_up.go`，前端为 `iot_front/src/duty/`、`src/components/duty/` 和 `src/views/DutyManagementView.vue`。

附件原件在 MinIO 的 `iot-duty-attachments` 桶，单文件不超过 16 MiB，对象键由服务端生成。数据库保存不可变上传元数据，记录只能引用已上传且属于本人当前班次的附件，下载不接受任意对象桶或 URL。PDF 读取指定冻结版本，签署后附录单独标识；CSV 包含该版本全部事件，并处理电子表格公式注入。

## 运行与备份

API 启动沿已有 PostgreSQL 迁移创建值班表。更新 API、Web、备份服务与 Harness，使内置 Manifest 和工具策略一起生效；具体步骤见 [部署与本地调试](DEPLOYMENT.md)。人工排班、记录、交接和导出不依赖模型连接，AI 与知识向量仍需外部 HTTPS API。

老排班使用一次性 CSV 导入：先预览账号映射、日期、时区、模板、岗位、人员及冲突，再按摘要导入。导入不自动发布、不复制旧密码，也不建立双系统同步。

值班资料及引用附件纳入 FULL 备份，旧版本和每日设备备份的覆盖不同，详见 [备份范围与隔离恢复](BACKUP.md)。专项测试、真实 PostgreSQL 条件和浏览器隔离夹具统一见 [值班管理回归](DEVELOPMENT.md#值班管理回归)。
