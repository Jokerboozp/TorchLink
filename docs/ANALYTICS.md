# 五项业务分析

[共同契约](#共同契约) · [数据质量](#数据质量) · [监测连续性](#监测连续性) · [策略实验](#告警策略实验台) · [演练复盘](#演练与复盘) · [维护投入](#维护与投入) · [开发入口](#开发入口)

五个应用共用持久事实任务和固定快照，确定性计算、人工核实与 AI 解读分别保存。设备与生产告警继续走原有业务链路；模型关闭或失败时，事实计算、人工流程和报告仍可使用。

| 页面入口 | 用途 | AI 工作流 |
| --- | --- | --- |
| 运行监控 → 数据质量；设备详情页签 | 核对格式、量程、完整性、时钟和序列变化，确认基线与校准依据 | `data-quality-analyst` |
| 运行监控 → 监测连续性；设备详情页签 | 分别检查连接、接收、有效数据及登记的接入依赖 | `monitoring-continuity-reviewer` |
| 告警规则 → 策略实验 | 固定数据集比较当前规则与禁用候选，人工核实后明确发布 | `rule-policy-analyst` |
| 运行监控 → 演练与复盘；告警详情建立案例 | 固定流程和实际节点，确认复盘并独立验收整改 | `response-reviewer` |
| 运行监控 → 维护与投入；设备详情 | 实物与维修、独立功能验收、前后观察、透明投入排序与人工决定 | `maintenance-outcome-reviewer`、`maintenance-investment-advisor` |

反复报警核查使用同一分析基础，独立的模板、活动、措施与轮次见 [反复报警治理](ALARM_GOVERNANCE.md)。

## 共同契约

创建任务必须显式选择设备和时间区间，即使管理员也不能用空集合表示全租户。UTC Unix 毫秒表示时间，区间为 `[start,end)`，持续时长使用 `xxxMs`。来源分别保存设备事件时间 `eventAt`、平台接收时间 `receivedAt`、成功持久化确认后的可用时间 `availableAt`；旧 `processed_at` 只提供处理阶段依据，缺失凭据保持未知。

首次执行固定配置版本、成员身份、源值哈希、来源截止点和覆盖，后续接管、查询与导出使用同一版本。PostgreSQL 事实读取使用一致性事务；ClickHouse 单独记录读取截止与覆盖，不声明跨库共同事务。新增晚到数据不进入旧任务；需要纳入时重算成新任务。原来源删除或改变时保留缺失和部分覆盖，不改旧指标或事实哈希。

任务状态为 QUEUED、PREPARING、RUNNING、SUCCEEDED、PARTIAL、FAILED、CANCELLED。页面显示实际阶段与处理数量，支持停止、刷新恢复和新版本重算。共享 PostgreSQL 通过租约、递增令牌、检查点和输出共同提交协调副本；旧领取者不能读取或提交新租约的结果。达到来源或时间上限时明确裁剪及不可计算项。队列、worker、窗口与读取限制见 [业务分析任务配置](DEPLOYMENT.md#业务分析任务)。

读取、计数、附件、导出和模型工具重新检查当前租户、菜单、操作及完整设备集合。范围收窄后，包含未授权成员的整份旧任务及正文不可读；资金和引用质量资料的派生报告还继承来源读取权限。更新携带当前版本，重复动作使用持久 `idempotencyKey`；同键不同请求或版本冲突返回 409。列表默认 20、最多 100 条。

AI 由用户显式启动，运行绑定固定快照、`factsHash`、任务、租约、发起人和当前权限。受控 `query_analysis_snapshot` 只能读取绑定工作流实际允许的事实，知识沿用 Agent 绑定和首次调用前的授权检索。模型仅引用本次提供或受控工具读过的事实，指标由服务端计算；非法结构、无效引用、撤权、停止和无法确认的中断响应只使独立 AI 版本失败。六个工作流的 token 上限为 8192。AI 不发布生产规则、控制设备、完成验收或作出资金决定。

## 数据质量

入口为“运行监控 → 数据质量”，设备详情也提供当前设备的数据质量页签。先完善产品物模型，再保存个人或受权共享质量配置，明确测点、单位、量程、周期及固定时间锚点。事件上报不计算固定周期缺槽。统计最低样本数为 30，物理阈值和偏差方法须明确配置；没有依据的维度显示未知或不适用。

基线从指定设备与配置版本的真实已存测量生成，人工确认保存新版本；未经确认的基线不参与漂移判断。校准记录保存依据、人员和附件，附件通过平台的当前权限校验下载。页面能建立版本、选择任务范围、查看实际处理数量、停止任务、刷新后恢复进度、重算为独立新任务及追加人工核实。

新分析表只存元数据、指标及必要代表证据，测量值留在原存储。设备事件时间与平台接收时间分别形成预期序列；同槽重复不增加覆盖，容忍必须小于半周期。

窗口结果分别展示格式、范围、双时间完整性、时钟、稳定段、变化率、偏离、漂移及解析依据的数量与分母。序列在单位、协议、配置、工况变化和长缺口处断开。MAD 为零时使用明确的绝对容忍依据，否则保留未知；CUSUM 只采用已确认且匹配的有效基线。曲线保留事件、接收和可用时间，标明原成员总数与实际展示点数；均匀抽样显示不改变统计分母。

`/api/v1/data-quality` 下的 `profiles`、`baselines`、`calibrations` 管理配置，`runs` 创建并读取持久任务，任务的 `metrics`、`findings`、`evidence`、`series` 和 `reviews` 提供结果。`findings/:id/reviews` 追加核实，`runs/:id/export` 下载固定 JSON 报告并包含当前获权的核实记录，不重新计算。附件只接受服务端保存的引用。

数据质量 AI 输出解释、建议核查和限制（`interpretations`、`suggestedVerification`、`limitations`）。重复启动复用当前版本，显式再次解读产生新版本；知识配置遵守 [共同契约](#共同契约)。

## 监测连续性

入口为“运行监控 → 监测连续性”，设备详情也提供相应标签。设备范围继续要求设备管理读取权限、应用菜单和明确的设备授权。个人策略或受权共享策略固定关键测点、可接受报文类型、有效条件、ALL / ANY、周期及容忍；人工重要性只作为明确标签。事件上报没有固定周期时不计算可用率。

任务分别保存连接、平台接收和有效数据三条时间线。收到的测量使用 `receivedAt` 建立接收区间；有效数据从真实 `availableAt` 起算，并在 `eventAt + 周期 + 容忍` 到期。延迟解析和旧数据重放不能填补此前的实时数据缺口。缺失可用时间、窗口前状态、来源历史或读取超限时保留未知和部分覆盖，不转换成正常。已知区间可用率与已知覆盖率并列，只有未知为零才给完整窗口可用率。

观察资料先保存未确认版本，有权限人员确认后才作为运行、停运和检修依据；停运及检修排除区间取并集，设备自身离线保留在分母。结果分别展示逐属性与固定合并策略、最长缺口、次数、原文最后解析结果及来源完整性。分辨率保护只减少时间线代表区间的展示，不改变完整计算分母；实际处理数量和被省略数量分别披露。

依赖来自实际登记的主子设备、接入配置和 Collector。历史关系按有证据的有效区间分段；无历史依据时只保存当前资料的 `CURRENT_ONLY` 快照，不能将当前关系用于过去时段。父设备必须单独获权，组卡片只展示本任务成员，集中比例分母为本次明确设备数。假设影响绑定组 ID、资料时点及快照哈希，结果仅说明登记的依赖集合。共同缺报采用固定门槛的重叠和 Jaccard，不能据此判断共同原因、消防保障或冗余能力。

`/api/v1/monitoring-gaps` 下的 `profiles`、`observations` 保存版本，`observations/:id/confirm` 确认观察资料，`runs` 创建持久任务；任务的 `intervals`、`dependency-groups`、`metrics`、`findings`、`evidence` 分页读取固定结果。`hypotheses` 保存幂等假设，`findings/:id/reviews` 追加人工核实，`runs/:id/export` 下载已存报告。可以引用已完成且完整获权的数据质量版本，跳转按固定运行 ID 读取，不回退到其他缓存任务。

连续性 AI 输出观察到的薄弱处、核查顺序、依赖观察及限制（`observedWeaknesses`、`prioritizedChecks`、`dependencyObservations`、`limitations`）。依赖结论绑定本次组成员，不能扩大为全部系统的可靠性结论。

## 告警策略实验台

入口为“告警规则 → 策略实验”。仅有实验菜单和明确设备范围的用户也可进入；基线读取使用 `/api/v1/rule-lab/rule-sources?deviceIds=...`，按不可变规则版本自身的产品及当前设备范围裁剪，不扩大生产规则管理权限。设备集合分批读取时按版本 ID 去重，累计结果须遵守响应 `maxRecords` 给出的实际读取上限；规则改换产品后，已固定的旧版本仍按原产品判断是否适用。带有未授权摄像头的源版本不可用于该任务。生产规则历史与发布继续要求规则管理权限及当前全设备管理范围。

固定数据集保留完整标准消息、三个时间、协议、点表、配置、单位及源值哈希，包括直接设备报警和部件事件。首次执行在持久检查点中冻结全部输入，后续读取与接管使用同一份数据；新晚到记录和来源删除不改变旧数据集。窗口及热身区间明确，空初态与缺少历史记录保留未知。历史注册只有当前生效依据；不以当前版本补造过去历史。

实验版本绑定数据集、基线版本、禁用候选、假设、固定标签及评价策略。两条分支使用独立持续条件、告警、幂等与部件状态，只产生实验周期和动作意图；不写生产告警、通知、原始队列或设备控制。原始事件时间、平台接收时间与真实执行阶段时间分开。完整执行 trace 的规则顺序、阶段时钟、初态和来源一致时才声明 `EXACT`；其余为 `HISTORICAL_SIMULATION` 并展示限制。热身只初始化，不计入主窗口结果。

标签先保存未确认版本，再人工核实。真实正例、已核实负区间、未知和评估窗口固定为两条分支的共同分母；UNKNOWN 不当负例，无充分核实负样本时不输出精确率。周期匹配先最大匹配数量，再最小总时间误差，最后按稳定 ID 消除同值；重复触发和独立周期分别展示。校准与留出样本用途明确，留出集合重复使用时披露已失去独立性。

生产新语义版本为 `processing-multistage-revisioned-retain-open-v2`。原子发布检查 `expectedBaselineVersion`、固定实验候选和当前权限，版本冲突返回 409；回滚来源必须属于同一规则并与实际正文一致。发布清除旧 pending；禁用或删除保留尚未解除的 ACTIVE / ACKED 告警。ACTIVE 自动恢复使用创建告警的规则版本；ACKED 保持既有自动恢复语义。已有告警若没有创建版本则标记 UNKNOWN，不能补造旧历史。直接报警与部件转换的 trace 同状态、Watermark 和 outbox 原子保存，最终完成 trace 与消息处理完成共同提交；部分尝试不能宣称精确再现。

`/api/v1/rule-lab` 的 `datasets` 创建和读取固定输入，`experiments` 保存不可变候选，`experiments/:id/runs` 创建运行，`runs/:id` 下的 `metrics`、`outcomes`、`diffs`、`labels`、`findings`、`evidence` 读取固定结果；`labels/:id/confirm` 保存人工确认。实验报告导出绑定固定完成运行。AI 解释两分支行为差异与核查建议；生成的候选草稿只能以禁用正文保存成新实验版本，比较/发布启用状态独立固定。草稿保存与 AI 成功提交同租约事务，失败或停止不能留下成功草稿；正式发布由人员按固定实验的启用状态明确执行。

## 演练与复盘

入口为“运行监控 → 演练与复盘”，告警详情可建立当前获权告警的真实案例。流程保存不可变版本，发布前校验步骤、实际岗位、前置关系、计时起点与必要证据。草稿计划可以修改；开始时固定已发布流程和当前有效人员，后续流程改版不升级已有执行。获授权的非当班人员可以参与演练和承担整改。

模拟事件只写演练执行对象，不进入 RawMessage、解析、生产告警或通知链路。真实案例从已授权告警及具体单次上报建立；平台接收起点只取匹配原始报文身份的实际接收时间，没有证据则保留未知。单次资料分类需要明确来源、依据和核实状态；含生产事件保留 PRODUCTION，不把整个设备时段或聚合告警排除。

人工节点分别保存实际发生和平台登记时间、执行人与记录人、依据及状态。系统节点只接受已提交生产事务的真实类型和时间；ACK 只能证明平台确认。更正追加独立记录，未经核实、缺必要证据、前置未确认或发生倒序的节点不作为有效完成或正向耗时。尚无动作记录不等同现场未执行，等待量与未知计时分别展示。

`/api/v1/response-procedures` 管理流程，`drills` 管理计划，`response-cases` 建立真实案例；`response-runs/:id` 提供执行状态、节点、更正、单次资料关联和附件。`response-staff` 按当前有效账号及完整设备范围列出人员，`evidence-candidates` 还检查告警或原文菜单。附件使用私有桶、服务端引用、内容哈希和独立下载权限。写入和重试遵守 [共同契约](#共同契约)。

执行的 `evaluations` 保存固定资料截止、源执行版本和事实哈希；`response-evaluations/:id` 读取原结果。正式确认绑定运行版本和事实哈希，迟到登记另生成新评估，不改旧报告。整改仅从已正式确认报告中的实际问题建立，采用独立负责人和 OPEN / IN_PROGRESS / PENDING_VERIFICATION / DONE / CANCELLED 生命周期。通过规定验收项的独立验收操作才能完成，失败返回处理中，归档执行不关闭整改。存在实际 ACTIVE 值班时可关联当班跟进条目；当班完成不通过主业务验收。值班页面的业务主事项目录按原对象读取主责和状态，先过滤范围再分页计数。

复盘 AI 输出实际瓶颈、证据缺口、改善建议与限制。历史作业绑定原评估版本，不能切换为当前最新执行；正式确认及独立整改仍由人员完成。

## 维护与投入

入口为“运行监控 → 维护与投入”，设备详情和当班业务主事项目录可以进入对应设备或维修记录。实物与平台设备分别保存：制造、安装、投运和退役日期来自实际资料，未提供时保持未知，不从平台注册日期推算年限。确认实物区间使用原子占位版本，重叠创建或更换发生版本冲突时整批回滚；更换可以沿用设备 ID，但旧、新实物版本和切换边界分别固定。部件身份只接受已有生产资料中的稳定关联。

维修采用 DRAFT / IN_PROGRESS / COMPLETED / CANCELLED。实际发生时间与服务器登记时间分别保存，补录不改变登记时钟。结束工作只完成记录；功能验收单独保存规定项目、实际检查项、结果、人员和证据，不能用重新在线或当班事项完成代替。可关联已经确认的整改及实际 ACTIVE 当班跟进，已结束工作仍可建立独立跟进，取消记录拒绝新关联；主业务状态始终从维修或整改对象读取。写入携带版本及持久幂等键，多副本与重启后的重试返回原结果。

变化观察固定前后实物、区间、维修版本、已确认工况、产品或故障类型的比较准入、质量快照及实际来源截止。故障只采用具体 ALARM_CREATED 周期及核实后的类型和生产分类，重复上报不增加周期，事件归属使用对应标准消息的事件时间；没有可信时钟或来源覆盖不能补为零故障。状态未知、缺少起点、原始资料过期和裁剪分别披露，迟到资料不改旧报告。

有效小时先与实物区间求交，再扣除有依据的计划停运、已确认测试和平台观测不可用区间的并集；设备自身离线留在分母。结果并列数量、有效小时、故障来源覆盖、已知离线比例、状态覆盖和未知时长。准入缺失、覆盖不足、短窗口或功能验收未确认时保留证据不足；规则、协议、网关、测点、周期和工况变化保留混杂。达到准入也只允许描述性比较，不证明维修因果、消防风险或寿命。固定补充资料展示再次出现时间、重复维修、实际验收、已引用质量快照及获权的分币种历史成本。

投入方案采用固定策略 `required-tier-transparent-v1`：人工确认必需分层，层内依次采用当前未解除的已核实功能缺陷、人工重要性、同口径确认故障率、已知离线小时及稳定实物 ID。证据不足的指标进入同层待补资料区，不能称为低风险；费用和年限不暗中参与加权。人工排序调整、候选动作和最终决定均保存理由；DECIDED 只表示人员决定。

费用以精确十进制记录 ESTIMATE / ACTUAL、币种、发生日期、规划区间和依据，未知不填零，工时不折算金额。单个资金方案只采用一种币种和同规划范围的实际报价，逐项累计并披露超预算缺口；缺报价时后续纳入状态也保持未知。历史实际支出不当成未来报价，不给生命周期优势或 ROI。资金读取使用独立 `GET /api/v1/maintenance-costs` 权限；含资金的配置、排序、理由、报告与 AI 正文整份继承该权限。引用质量资料还继承其读取权限，撤权后拒绝旧派生版本；普通版本须以普通输入重新计算。

`assets`、`maintenance-records`、`maintenance-contexts`、`maintenance-admissions`、`maintenance-fault-cycles`、`maintenance-costs` 和 `investment-scenarios` 管理不可变资料版本。维修的 `actions`、`verifications`、`observations` 及当班关联分别处理业务；`maintenance-observations`、`investment-evaluations` 提供固定任务、快照、明细、核实与导出。方案的 `evaluate`、`adjustments`、`decisions` 和 `actions` 形成透明试算与人工决定。私有附件由服务端保存身份和内容哈希。

维护 AI 解释观察变化、混杂与待核查项，投入 AI 整理优先级和人工决策考虑；两类输出分别保存。
