# 平台承压能力评估（2026-09-24）

## 结论

**本机已逐级加压并找到部分失效点，但仍不能给出生产环境的统一“最大并发用户数、最大接入设备数、最大持续消息量”。** 2026-09-24 在用户指定的本机 `127.0.0.1:8081` GoLand 调试进程及现有中间件上，读接口在 2,048 并发请求出现连接拒绝、4,096 并发时约 42.6% 请求连接拒绝；标准 HTTP 上报在 1,024 并发请求时约 23.0% 超过 5 秒超时。另一方面，20 万台设备登记和 1 万台 MQTT 同时连接均通过，尚未找到这两项的平台上限。测试条件与完整数据见下文；**这些数字不能直接换算成生产可承诺的在线用户数或活跃上报设备数**。

默认 `compose.yaml` 由单个 `platform-api`（`combined` 角色）接入并处理业务，Redpanda 为单节点、PostgreSQL/ClickHouse/EMQX 等也均为单实例。可选 `compose.access.yaml` 拆出 Access Gateway，但不能凭配置推算扩容倍数。下表同时列出本机实测下界和源码限额，两者含义分别说明。

| 问题 | 目前能确认的数值 | 含义与边界 |
| --- | --- | --- |
| 最多并发管理用户 / HTTP 请求 | **用户数未知；本机单账号 `/api/v1/events` 1,024 并发请求全部成功，2,048 开始失败** | 4,096 并发时 10,543/24,742 请求连接拒绝。测试时仅 12 条设备状态、2 条活动告警，且使用同一管理员令牌；不是 1,024 个独立用户的验收。 |
| 最多登记设备 | **本机至少 200,000 台；上限未找到** | 20 万条登记全部成功，就绪检查正常，结束后全部删除。此项只测登记，没有让 20 万设备连接或上报。 |
| 标准 HTTP/MQTT 上报活跃设备 | **单进程每滚动约 1 分钟最多 10,000 个不同设备键** | `onboarding.Service.Allow` 的内存表到 10,000 项后只清理超过 1 分钟的旧键；若这些键都仍活跃，新设备被限流拒绝。此限制按进程生效，不是集群保证，也不是登记数上限。 |
| 单台标准 HTTP/MQTT 设备上报速率 | **每进程每秒最多 20 条** | 超出会被限流；它不能推出全平台可处理 `10,000 × 20` 条/秒。 |
| 自定义 TCP 同时连接 | **每个接入 Profile 最多 128 个会话，实测吻合** | 第 129 个空闲连接被关闭，160 个连接时仍仅 128 个保持打开；测试没有发送有效业务帧。 |
| TCP/UDP 协议操作并发 | **每进程 32 个槽位** | `Listeners` 内的 Worker 操作限制，不能解读为只支持 32 台设备。 |
| MQTT 平台接收缓冲 | **每运行实例 10,000 条或 512 MiB，先到为准** | 8 个固定分片，每片 1,250 条/64 MiB；热点分片可先满。这是故障期间待处理报文容量，不是 MQTT 在线设备数。 |
| AI 对话并发 | **默认 Harness 1；Ollama 并行 1** | `deepseek-harness` 为可选 profile；启用后的默认配置如此。AI 容量独立于普通设备上报。 |

## 本机逐级压测结果

测试机为 Windows 11 专业工作站版、Ryzen 7 8845HS（16 逻辑处理器）、31.3 GiB 内存。目标 API 是本机 GoLand 的 `__debug_bin.exe` 调试进程，监听 `127.0.0.1:8081`；沿用当时现有 PostgreSQL、ClickHouse、Redpanda、EMQX 等中间件。负载生成器也运行在同一台 Windows 主机。各级均检查 `/health/ready`，达到明显错误或超时后停止该负载，避免把客户端端口耗尽误判为平台容量。以下是**这套本机组合在短时测试中的观测值**，不是长期稳态或目标服务器验收。

| 负载轴与测试方式 | 通过的级别 | 观测到的失效或边界 | 解释 |
| --- | --- | --- | --- |
| 管理端事件读取：同一管理员令牌，并发调用 `/api/v1/events`，每级约 8–11 秒 | 单生成器 1,024 并发：22,925/22,925 成功，约 2,774 次/秒，P95 427 ms；4 进程合计 1,024 并发：18,783/18,783 成功 | 8 进程合计 2,048 并发：18,131 成功、1,531 次网络错误（7.8%）；16 进程合计 4,096 并发：14,199 成功、10,543 次 `ECONNREFUSED`（42.6%），26 次就绪检查失败，成功请求最差进程 P95 3,420 ms | 是并发 HTTP 请求，不是独立在线用户；本机客户端、Windows TCP 栈和服务端共同构成边界。停止后就绪恢复 200。 |
| 设备登记：标准 HTTP 产品，32 个创建 worker，逐级增至 20 万条 | 50,000、100,000、200,000 均全部返回 201、0 失败，200,000 级新增 10 万条约 1,575 条/秒，P95 31 ms，就绪 200 | 未触发失败；本机**登记总量下界为 20 万台** | 只测登记，没有测这些设备上线、上报、状态查询或长期存储。压测结束删除全部 20 万条。 |
| 标准 HTTP 设备上报：1,000 个已登记设备，每级发送约 5 秒，5 秒请求超时 | 256 并发：1,358/1,358 返回 202，约 228 条/秒，P95 1,793 ms；512 并发：2,095/2,097 返回 202，2 次超时，约 296 条/秒，P95 3,366 ms | 1,024 并发：1,412/1,833 返回 202，421 次超时（23.0%），约 169 条/秒，P95 5,037 ms；就绪仍为 200 | 入口 202 是接受而非完成。两轮共收到 9,275 个 202；数据库最终落下 9,342 条测试原文，其中包括 67 条客户端超时后仍被服务端接受的请求。这 9,342 条后来全部尝试解析、0 解析错误、标准消息全部完成处理。测试结束时短暂 `UNPARSED` 属异步积压。短时速率不能称为持续吞吐。 |
| MQTT 设备认证连接：独立设备凭据连接现有 EMQX | 10,000 台同时保持连接，0 失败，就绪 200 | 继续向 15,000 台加压时，仅 10,702 条连接保持，4,298 次客户端 `EADDRINUSE`；就绪 200 | Windows 负载机临时端口耗尽，不能据此认定 EMQX 或平台的连接上限；**可证实下界为 1 万连接**，不代表 1 万台同时上报可持续。 |
| 自定义 TCP 监听：专用临时 Profile，打开不发送有效帧的空闲 socket | 128 个会话保持打开，就绪 200 | 第 129 个连接被关闭；尝试 160 个时仅 128 个仍打开 | 验证单 Profile 会话上限，没有测自定义协议解析吞吐。 |

为核对持续上报，另以 1,000 台设备、128 并发请求运行 60 秒：13,395/13,395 请求返回 202，入口平均约 222 条/秒，P95 1,012 ms，就绪 200。但阶段结束附近，读取原文归档索引时已见约 1.4 万条测试原文、仅约 649 条标记为已尝试解析；**入口接受速度明显高于异步解析速度**。随后 256 并发阶段因积压扩大而主动中止，未获得完整级别的延迟/成功率数据。两阶段合计产生 23,485 条测试原文；停止发送后十余分钟，解析尝试与标准消息处理才全部追平到 23,485 条，解析错误 0。故不能把 222 条/秒写成可持续端到端吞吐，也不能把健康检查 200 当成链路无积压。

**清理与恢复核验：**测试创建的 20 万登记设备、1.5 万 MQTT 登记设备、3,000 台 HTTP 上报测试设备和临时 TCP Profile 均已删除。两轮短时上报的 9,342 条与持续上报的 23,485 条原文及后续标准消息都完成处理后，压测数据、设备状态和事件已定向清理；按压测前缀查询 PostgreSQL/ClickHouse 均为 0。最终 API 设备总数恢复为 14，`/api/v1/events` 为 12 条设备状态、2 条活动告警，`/health/ready` 返回 200。本机测试没有重启服务。

原始逐级结果保存在 [capacity-2026-09-24](testing/capacity-2026-09-24/) 目录，包括 `events-results.jsonl`、`events-multi-results.jsonl`、`registry-results.jsonl`、`ingest-results.jsonl`、`mqtt-results.jsonl` 和 `tcp-results.jsonl`；本机 `data/capacity-run/` 保留执行脚本。第一轮上报脚本用错详情查询 ID，生成的 `HTTP_404` 样本状态是脚本错误，已修正并以数据库完成计数复核，不计为平台失败。

## 容量的核心关系

设备规模需要同时满足**连接数、单位时间上报数、处理与落盘速度、保留周期、管理查询开销**。若每台设备每 `T` 秒发送一条，则入口平均速率为 `设备数 / T` 条/秒；告警、部件状态、原文归档、规则及 AI 会增加单条成本。

| 假设场景（仅算术，不代表平台已通过） | 平均入口速率 | 对现有单进程标准接入的判断 |
| --- | ---: | --- |
| 1,000 台，每 60 秒 1 条 | 约 16.7 条/秒 | 未触及设备键数上限；端到端处理能力未验证。 |
| 10,000 台，每 60 秒 1 条 | 约 166.7 条/秒 | 已到活跃设备键数上限；任何新增活跃键都可能被拒绝。处理能力未验证。 |
| 100,000 台，每 10 分钟 1 条，完全均匀错峰 | 约 166.7 条/秒 | 平均流量相同，但每分钟恰有 10,000 个不同键，处于限流表边界；不能据此宣称支持 10 万台。 |

例如按每条原始载荷 1 KiB、166.7 条/秒计算，**仅载荷**约 13.7 GiB/日（约 14.7 GB/日）。数据库行、索引、WAL、标准消息、告警、备份及副本额外占用未计入。实际容量规划必须按代表性报文大小和留存期限测量。

## 主要瓶颈和风险

1. **标准设备键数有硬限额。** `internal/onboarding/service.go` 的计数器同时限制每设备 20 条/秒和每进程最近约 1 分钟 10,000 个键。多副本各自计数，无法当作全局统一限流或可靠的线性扩容方案。
2. **管理端在线人数会放大读负载。** 前端在上一次请求结束后 3 秒再次请求 `/api/v1/events`；该接口读取租户全部设备状态和活动告警，随后按权限过滤并返回。设备多时，单个响应及数据库读取都随设备数增加；`U` 个在线用户在接口快速返回时约产生 `U/3` 次此接口请求/秒，还未计入设备列表、总览和详情。当前没有“百/千用户同时在线”的实测结论。
3. **自定义 Go 协议逐次启动子进程。** 接入的 `ingress`、解析的 `decode` 和命令的 `encode` 都执行独立 Worker；启动成本使这类协议的吞吐无法直接套用标准 JSON 路径。TCP/UDP 入口有 32 个并发操作槽，Kafka 原文处理侧仍需单独测量。
4. **异步链路不能用入口成功率代替完成率。** `IngestRaw` 归档后发布到 Kafka；当前 `Bus.Subscribe` 每个订阅在一个 goroutine 中逐条处理并提交。虽然默认主题有 12 分区，单进程单订阅不会因此自动得到 12 路应用处理并行度。必须同时看 Kafka 积压、解析完成延迟和告警完成延迟。
5. **缓冲上限不是持续吞吐。** MQTT 本机持久接收队列 10,000 条/512 MiB；后端处理速度长期低于入口速度时仍会填满。按 1,000 条/秒净积压，10,000 条只够约 10 秒（忽略大小限制）。设备收到 Broker PUBACK 也不能证明业务处理完成。
6. **监控不足以直接读出峰值。** 当前 `/metrics` 包含归档计数、MQTT 待处理数等，但没有端到端延迟分位数与管理 HTTP 请求分位数；`kafka_lag` 指标在当前源码中有定义，未发现实际更新调用。压测需另外采集 Broker/数据库/系统指标。

## 源码核对与证据

- 版本：`main`，提交 `9763c6d7`；工作区有其他任务的未提交源码修改，本报告未触碰它们。
- 本机 `http://127.0.0.1:8081/health/ready` 在测试前后返回 `status: ok`，已配置的 `archive/eventBus/knowledge/realtime/repository` 检查为 `ok`。就绪检查仅说明检查时依赖可达，不能代替业务成功率与异步完成率。
- 代码依据：`internal/onboarding/service.go`（限流）、`internal/protocolruntime/listeners.go`（会话及操作槽）、`internal/adapters/mqtt/inbox.go`（持久队列）、`internal/httpapi/user_events.go` 和 `internal/adapters/postgres/repository.go`（全量状态读取）、`internal/parser/external.go`（逐次 Worker）、`internal/adapters/kafka/bus.go`（订阅消费）。部署依据：`compose.yaml`、`compose.access.yaml`。
- `cmd/loadgen/main.go` 的 `-rate 1000`、`-burst-rate 50000`、`-devices 10000` 都只是**生成器默认输入**。HTTP 路径调用管理员 `/api/v1/raw-messages`，MQTT 路径使用管理员压测令牌；它们不能单独验证标准设备凭据、设备在线连接数或完整业务吞吐。

## 要得到生产可承诺的“最多多少”，仍需完成的测试

1. 固定目标硬件、磁盘类型、网络、Compose 形态、数据库保留周期、报文大小、协议比例、在线用户数和业务规则比例；记录 CPU、内存、磁盘 IO 与中间件版本。
2. 在隔离压测环境预先登记真实数量的模拟设备，分别测试标准 HTTP、标准 MQTT、TCP 长连接和 Go 协议；覆盖 1,000、5,000、10,000 台，并逐级增大上报频率。设备数必须是已登记且成功认证的设备数，不能只设置 `loadgen -devices`。
3. 每级至少完成稳态、5 分钟突发和断流恢复，观察入口成功、Raw 落盘、Kafka 积压、解析/告警完成、MQTT 队列、数据库延迟和管理端 P95/P99；增加并发用户轮询。达到错误或积压持续增长时即为该条件下不可持续。
4. 明确验收线后再宣布上限，例如入口错误率、端到端完成时限、P95/P99 延迟、恢复时间与磁盘余量。报告须附压测命令、原始结果、机器配置及可复测日期。

**当前对外表述建议：**“在一台 Windows 开发机的调试服务和现有中间件上，已验证至少 20 万台设备可登记、1 万台设备可同时建立 MQTT 连接；管理事件接口在 2,048 并发请求开始出现连接错误，标准 HTTP 上报在 1,024 并发请求时约 23% 超过 5 秒。单进程标准上报另有最近约一分钟 1 万个活跃设备键的代码限制。正式上线容量需在目标服务器按真实报文和业务规则做稳态压测后确定。”
