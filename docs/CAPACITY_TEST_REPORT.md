# 全系统容量压测报告（2026-09-26，单机实测 + 集群预估）

本报告记录一次在本地隔离环境内的破坏性压测：从设备登记、HTTP / MQTT / TCP 上报、解析入库、规则与设备告警、管理端查询、智能巡检与 PDF、原文下载与回放到备份，逐项加压直到出现错误、超时、数据丢失或系统无法操作。压测方法与记录口径见 [容量压测方案](CAPACITY_TEST_PLAN.md)。

> 2026-09-27 已按第 6 节逐项修复（见 6.1），本报告的数字仍是修复前提交 `fe28f0db` 的实测，修复后尚未重新压测，默认配置下的上限预计变化，需按第 8 节重测后更新。
>
> 单机数字均为**本次实测**，只对第 1 节的硬件、提交与配置成立；第 5 节的集群数字是依据实测单条成本做的**推算**，未在集群上验证，不能作为对外承诺。

## 0. 结论速览

**整体承压能力（单机，默认配置 = 仓库 Compose 原样）**：端到端（接收 → 解析 → 入库 → 规则）可持续约 **45 条/秒**；超过后接收仍返回 202，但积压持续增长、端到端延迟从 0.2 秒升到数分钟。只调环境变量（第 3.3 节）可到约 **100–110 条/秒**。按设备上报周期折算：默认配置约 2,700 台 × 每分钟 1 条，或 13,500 台 × 每 5 分钟 1 条。

| 功能 | 单机实测上限（默认配置） | 首先出问题的环节 / 失效方式 |
| --- | --- | --- |
| 设备登记（onboarding） | 约 380 台/秒（设备 <6 千）；约 180 台/秒（设备 9.5 万） | 全局 PostgreSQL 咨询锁串行化，加副本也不能提高 |
| HTTP 设备上报·接收 | 约 210–285 条/秒 | 同一分钟内活跃设备 >10,000 时返回 429；4,096 并发时 11.6% 连接被重置 |
| 解析 + 入库（端到端可持续） | **约 45 条/秒**；调优后约 100–110 条/秒 | 存储消费者受 PostgreSQL 连接池（默认 8）与逐条同步写限制 |
| 规则告警风暴（50% 报文翻转告警） | 低于 40 条/秒即积压；约 8 条告警/秒 | 同上；AI 自动研判队列约 0.5 条/秒，全面滞后 |
| MQTT 连接（单 EMQX） | 默认约 2 万时 **EMQX 崩溃**；放开文件句柄后实测保持 69,416 条 | 容器 `nofile=20480` 触发 `emfile`；约 28 KB/连接 |
| MQTT 上报·平台接收 | 约 25 条/秒无丢失；200 条/秒时 **47% 被 Broker 丢弃** | 平台订阅会话队列 1,000 条上限，设备已收到 PUBACK |
| TCP（GB26875 协议包） | 约 105 帧/秒；**每监听 128 个会话** | 第 129 个连接起被静默重置，自动登记止于 128 台 |
| 管理端列表 / 详情 | 详情类 3,000–7,900 次/秒；总览约 27 次/秒；原文列表约 40 次/秒 | 总览、原文列表、设备登记列表最先变慢 |
| 设备范围受限用户 | 告警列表约 14 次/秒（管理员 920）；设备列表约 22 次/秒 | 设备范围过滤成本高 |
| 实时提醒 `/api/v1/events` | 约 50 次/秒；每次 16 MB | 全量活动告警 + 全部设备状态；每个打开的页面每 3 秒轮询 |
| 普通用户登录（bcrypt） | 约 90 次/秒 | 占满 API CPU，其他接口 P95 升到 7.8 秒 |
| 智能巡检 | 9 万设备单次 3.8 秒，返回 21 MB | AI 建议因未配置密钥失败（见第 6 节） |
| 巡检 PDF 下载 | 峰值约 0.6 份/秒；单份 143 MB / 11,377 页 | 16 并发 P99 81 秒；报告缓存过期时 16 并发全部 502 |
| 原文批量下载 / 回放 | 100 条批量 3.6 秒；回放约 25 条/秒（申请 1,000/秒） | ClickHouse 原文按 ID 查询需扫描 |
| 全量备份 | 14 秒，44 MB（PostgreSQL 1.2 GB 规模） | 本规模未见瓶颈 |

压到“系统无反应或无法操作”的场景：PDF 与原文查询把 ClickHouse 打满后业务接口 20 秒超时（`/health/live` 仍 200）；Kafka 消费协程退出后解析永久停止（就绪检查仍 ok）；EMQX 在约 2 万连接时崩溃重启；PostgreSQL 连接耗尽后设备收到 401、报文被标记解析失败。详见第 4 节。

口径：

- “接收”指 HTTP 202 / MQTT PUBACK / TCP ACK；“端到端可持续”指在 60 秒阶梯内 `kafka_lag`（解析与存储消费组）不持续增长。
- 读接口使用闭环并发阶梯（1→256，每档 15 秒），同时每 500 ms 探测另一个管理接口，观察互相影响。
- 客户端与 API 同机：极高并发时的连接重置、临时端口耗尽部分来自客户端，已在对应位置说明。
- 本次使用的工具版本在请求达到自身超时后未计入失败，而是结束该工作协程；因此以超时为主的档位（PDF 32 并发、HTTP 上报 1,024 并发以上、总览与原文列表 256 并发）的错误率是**下限**，实际失败更多。提交到仓库的版本已改为计入 `timeout`。

## 2. 被测链路

```
设备 ─HTTP(凭据)─▶ API 接收 ─┐
设备 ─MQTT(JWT)─▶ EMQX ─▶ 平台订阅 → 磁盘持久队列 ─┤→ 原文归档(PG/CH) + 幂等索引 → Redpanda
设备 ─TCP(GB26875)─▶ 监听 → Go Worker ingress ─┘                               │
                                   解析消费者(parser) ◀──────────────────────────┘
                                   存储消费者(storage)：标准消息、遥测(CH)、设备状态(PG+Redis)、规则
                                   告警 → AI 自动研判队列 → Harness
管理端：列表 / 详情 / 总览 / events 轮询 / 巡检 / PDF / 下载 / 回放 / 备份
```

## 3. 各功能实测结果

### 3.1 设备登记（`POST /api/v1/onboarding`）

| 条件 | 并发 | 速率 | P50 / P99 |
| --- | --- | --- | --- |
| 设备 <6 千 | 4 | 382 台/秒 | 9 / 32 ms |
| 设备 <6 千 | 256 | 382 台/秒 | 655 / 759 ms |
| 设备 2–5 万 | 16 | 322–350 台/秒 | 42 / 114–132 ms |
| 设备约 9.5 万，链路空闲 | 16 | 178 台/秒 | 84 / 204 ms |

- 并发从 4 提到 256 吞吐不变、延迟线性增加：`internal/adapters/postgres/onboarding.go:17` 的 `pg_advisory_xact_lock(728194601)` 使所有租户、所有副本的登记串行执行（代码注释说明是为监听端口预留）。这是全集群上限，增加 API 副本不能提高。
- 设备越多登记越慢；批量导入 10 万台约需 5–10 分钟。

### 3.2 HTTP 设备上报（设备凭据认证）

闭环并发，20,000 台设备轮流上报（首轮，`d6c3e656` 工作区）：

| 并发 | 成功 202/秒 | 错误率 | P50 / P99 | 说明 |
| --- | --- | --- | --- | --- |
| 4 | 56 | 0 | 70 / 128 ms | 单条约 70 ms |
| 16 | 143 | 0 | 109 / 226 ms | |
| 64 | 205 | 31.9% | 217 / 629 ms | 全部为 429 |
| 128 | 212 | 52.4% | 215 / 1,132 ms | 全部为 429 |

- 429 原因：`internal/onboarding/service.go` 的进程内限流表最多 10,000 个设备键，只清理 1 分钟未更新的键。205 条/秒 × 60 秒 ≈ 12,300 台不同设备，超出后新设备被拒。**单个 API 进程每分钟最多服务约 1 万台不同的活跃设备**（标准 HTTP / MQTT 上报共用）。用 5,000 台设备重测后无 429。
- 极限测试（5,000 台设备，默认配置）：

| 并发 | 成功/秒 | 错误率 | P99 | 同期解析/秒 | 管理端探针 P95 |
| --- | --- | --- | --- | --- | --- |
| 256 | 252 | 0 | 2.8 s | 38 | 0.6 s |
| 1,024 | 267 | 2.8% | 9.1 s | 23 | 1.1 s |
| 2,048 | 284 | 3.4% | 9.9 s | 21 | 1.1 s |
| 4,096 | 253 | 11.6% | 9.9 s | 22 | 1.0 s |

接收上限约 250–285 条/秒；API 不崩溃，管理端仍可用。但**接收没有背压**：高压接收把解析吞吐从约 100 条/秒挤到约 22 条/秒，160 秒积压 5.1 万条，停压后约 15 分钟才消化完。

### 3.3 解析与入库（端到端可持续吞吐）

开环恒定速率、5,000 台设备、每档 60 秒：

| 速率 | 默认配置：积压变化 | 调优（池 64 / 通道 64）：积压变化 |
| --- | --- | --- |
| 50 条/秒 | 4 → 206（缓慢增长） | 0 → 11（平稳） |
| 75 条/秒 | 213 → 1,848 | — |
| 100 条/秒 | 1,848 → 4,355 | 1 → 24（平稳） |
| 150 条/秒 | 4,355 → 10,438 | 24 → 3,090（增长） |
| 200 条/秒 | — | 3,090 → 6,969 |
| 300 条/秒 | — | 6,969 → 23,239（接收 279/秒，解析 202/秒） |

- **默认配置可持续约 45 条/秒，调优后约 100–110 条/秒。** 积压全部出现在存储消费组（`kafka_lag_storage`）。
- 瓶颈定位：pprof 阻塞分析显示协程主要阻塞在 `pgxpool.Acquire`；抽样协程栈显示每条标准消息在存储阶段依次执行 PostgreSQL 设备状态更新 / 认领 / 标记完成、Redis 状态、ClickHouse 合批写入（每批最长等待 20 ms）等 8–10 次往返，默认只有 8 条并行通道共享 8 个数据库连接。
- 调优后 100 条/秒时的平均 CPU：ClickHouse 约 2.2 核、PostgreSQL 约 1.3 核、API 约 0.35 核、Redpanda 约 0.23 核；ClickHouse 峰值瞬间可到 8 核。
- 连接池再加到 128 反而出错：超过 PostgreSQL `max_connections=100`，见第 4 节。
- 端到端延迟（每秒一条探针，入口到 `PARSED`）：空闲约 0.16 秒；积压时 20 秒、68 秒，最终超过 120 秒。

### 3.4 MQTT

| 项目 | 结果 |
| --- | --- |
| 设备取令牌 `POST /api/v1/device-mqtt/token` | 2,739–3,150 次/秒，0 失败（7 万台）；平台繁忙时降到 881 次/秒 |
| 宿主机单客户端连接 | 保持 16,167 条后客户端临时端口耗尽（客户端限制，非 Broker） |
| 容器内 5 个客户端，默认 Compose | 约 20,400 条时 **EMQX 崩溃重启**：`emfile`（容器 `nofile` 软限制 20,480），Mnesia 日志无法写入，所有设备和平台自身订阅断开 |
| 同上，`nofile` 放开到 1,048,576 | 保持 **69,416** 条认证连接，30 秒后全部存活；EMQX 约 1.9 GiB（约 28 KB/连接），连接风暴期 CPU 约 2.9 核；6.3 万以上连接 P99 20 秒，0.8% 连接超时；因设备用尽而停止，Broker 未到上限 |
| 令牌有效期 | MQTT / HTTP 连接方式的设备令牌 5 分钟，EMQX 配置 `disconnect_after_expire = true`：实测 5,000 条连接在签发 5 分钟后同时断开。N 台 MQTT 设备需要持续 N/300 次/秒的取令牌和重连，集中上线后每 5 分钟出现一次重连风暴 |
| EMQX 接收（QoS 1） | 1,961 条/秒无错误，P99 563 ms |
| **平台从 EMQX 接收** | 约 23–48 条/秒（默认配置）；持久队列最多 10,000 条 |
| **数据丢失** | 200 条/秒持续 50 秒：设备收到 9,824 个 PUBACK，平台订阅会话队列满（1,000 条）后 EMQX 丢弃 4,639 条（47%），平台指标没有体现。累计丢弃 62,855 条 |

结论：默认配置下 MQTT **无丢失的持续上报约 25 条/秒**；超过后的丢失只能在 EMQX 客户端统计 `dropped_msgs` 中看到。

### 3.5 TCP（GB26875 独立 Go 协议包）

源码 ZIP 上传、编译、样例校验与发布耗时 7 秒。每个压测连接代表一台设备，发送注册帧后循环发送部件状态帧，并等待平台在原文归档后返回 ACK：

| 连接数 | ACK/秒 | 错误率 | P50 / P99 | 说明 |
| --- | --- | --- | --- | --- |
| 8 | 106 | 0 | 66 / 195 ms | |
| 32 | 102 | 0 | 168 / 3,078 ms | 存储积压增长 |
| 128 | 51 | 80% | — | 大量 reset / EOF |
| 256 | 29 | 99.8% | — | 几乎全部被拒 |

- 每个监听最多 128 个会话（`internal/protocolruntime/listeners.go:26`），超出后连接被关闭且**不写日志**；自动登记恰好停在 128 台（含模拟器）。每进程另有 32 个 Worker 操作槽。
- 一台消防用户信息传输装置占一个会话，所以单个监听端口最多接 128 台；多台需要多个接入网关配置 / 端口。
- 设备主动火警（`ALARM_REPORT`）：16 连接、一半帧为火警，83 帧/秒无错误，60 秒内生成约 1,000 条部件告警。

### 3.6 告警

| 场景（默认配置） | 结果 |
| --- | --- |
| 40 条/秒，50% 报文使告警产生 / 恢复 | 解析 37/秒，约 8 条告警/秒，积压 +2,140/90 秒，上报 P99 6.5 秒，告警列表探针 P95 1.6 秒 |
| 80 条/秒，同上 | 解析 45/秒，积压 +7,269/90 秒 |
| 40 条/秒，5,000 台全部进入告警 | 约 8.5 条告警/秒，最终活动告警 7,602 条 |
| AI 自动研判（并发 1） | 未配置模型时每次也要走 Harness，只能处理约 0.5 条/秒；排队 6,000 条以上（约 3 小时）。接入真实模型后每条需要数秒到数十秒，告警风暴时自动研判必然滞后，只能作为事后参考 |

告警使存储阶段更重：默认配置在有告警翻转时可持续速率低于 40 条/秒。

| 8 并发 | 0.3 份/秒，P99 31 秒 |
| 16 并发 | 0.2 份/秒，P99 81 秒，管理端探针 P95 4.7 秒 |
| 32 并发 | 40 秒内无一完成 |
| 内存 | API RSS 峰值 2.3 GB |
| 缓存过期后 16 并发 | 每个请求都重新巡检，120 秒后全部 502；同时其他业务接口 20 秒超时 |

### 3.9 原文下载、批量下载与回放

- 批量下载 100 条 3.6 秒、200 条 5.8 秒；16 并发时 3.8 批/秒（约 380 条/秒）。
- 回放（`DRY_RUN`，申请 1,000 条/秒）实际约 25 条/秒：逐条从 ClickHouse 取原文。10 万条回放需一个多小时。
- 原因：`iot_raw_message` 的排序键为 `(tenant_id, device_id, received_at, message_id)`（`internal/adapters/clickhouse/repository.go:56`），按租户 + 报文 ID 查询无法利用索引，每次扫描租户全部数据。实测 3 分钟 485 次查询共耗 2,265 秒查询时间（平均 4.7 秒），每秒约 3 次这类查询即可把 ClickHouse 打到 400–690% CPU。PostgreSQL 分层（低频设备）的原文不受影响（详情 3,043 次/秒）。

### 3.10 备份

备份服务在宿主机运行，全量备份（PostgreSQL + ClickHouse + 原文 + MinIO）14 秒完成，产物 44 MB，接口同步等待完成。本规模下无瓶颈；未测恢复演练。

## 4. 失效方式与恢复

| # | 触发 | 现象 | 恢复 | 严重度 |
| --- | --- | --- | --- | --- |
| 1 | 宿主机临时端口耗尽时 Kafka 读取出错 | 解析永久停止：进程内**已没有任何 Kafka 消费协程**，接收仍返回 202，`/health/ready` 仍为 ok，无错误日志。`internal/adapters/kafka/consumer.go` 中 `FetchMessage` 出错即 `break`，不重建。正常重启 Redpanda 时消费会在约 40 秒内自行恢复 | 只有重启 API；原文和未提交偏移仍在，重启后补处理，无丢失 | 高 |
| 2 | MQTT 持续上报超过约 25 条/秒 | Broker 丢弃发往平台的报文（设备已收到 PUBACK），平台无指标 | 不可恢复（数据丢失） | 高 |
| 3 | EMQX 连接约 2 万（默认 `nofile`） | EMQX 崩溃重启，全部 MQTT 设备与平台订阅断开 | 自动重启后设备需重连 | 高 |
| 4 | 数据库连接池总和 > PostgreSQL `max_connections`（本次池 128） | 5,037 次 `too many clients`；设备上报收到 **401**（认证时数据库错误被当作凭据错误）、422、503；13 条报文因“protocol release not found”被**标记解析失败**，18 条归档失败 | 负载下降后自动恢复；失败报文需人工回放 | 高 |
| 5 | ClickHouse 原文按 ID 查询 + PDF | 业务接口 20 秒超时、就绪检查 503，ClickHouse `INSERT` 挂起约 4 分钟，`/health/live` 始终 200 | 停止查询后约 1–5 分钟恢复 | 中 |
| 6 | 接收速率长期高于存储能力 | 积压无上限增长，端到端延迟以分钟计；接收不降速 | 停压后按约 50–60 条/秒（默认）消化 | 中 |
| 7 | 集中登录（bcrypt） | API CPU 占满，其他接口变慢 | 登录结束即恢复 | 中 |
| 8 | 同一 TCP 监听第 129 个会话 | 连接被关闭，无日志、无指标 | — | 中 |

## 5. 集群化承压预估（推算，未实测）

### 5.1 哪些能靠加节点提升

| 环节 | 能否水平扩展 | 约束 |
| --- | --- | --- |
| API 接收 / 查询 | 能（多副本 + 负载均衡） | 限流表按进程计数（每副本每分钟约 1 万台活跃设备）；多副本不共享额度 |
| 解析 / 存储消费 | 部分能 | 每个主题 12 分区，同一消费组最多 12 个副本分得分区；每副本最多 64 条通道；最终受数据库限制 |
| 设备登记 | **不能** | 全局咨询锁，全集群约 200–380 台/秒 |
| PostgreSQL | 只能纵向扩（单主） | `max_connections` 必须 ≥ 各副本连接池之和，否则出现第 4 节 #4；建议前置 PgBouncer |
| ClickHouse | 纵向扩或分片 | 每 100 条/秒约 2.2 核，是单条 CPU 成本最高的组件 |
| Redpanda | 能（3 节点） | 默认 `--smp 1 --memory 1G`；每 100 条/秒约 0.23 核 |
| EMQX | 能（集群） | 每节点需放开 `nofile`；约 28 KB/连接 |
| 平台 MQTT 接收 | 取决于共享订阅是否在副本间分摊（未验证） | 单副本约 25 条/秒 |
| TCP 监听 | 增加监听端口 / 网关副本 | 每监听 128 会话、每进程 32 Worker 槽；不支持跨副本会话路由 |
| AI 研判 | 受模型并发与延迟限制 | 与平台节点数无关 |

### 5.2 推算依据与结果

以调优后实测的单条成本为基础：每 100 条/秒端到端约需 ClickHouse 2.2 核、PostgreSQL 1.3 核、API 0.35 核、Redpanda 0.23 核（无告警翻转）。以数据库 CPU 占用 70% 为安全线：

| 形态（示例） | 端到端可持续（无告警风暴） | 折算设备数（每 60 秒 / 每 5 分钟 1 条） | 前提 |
| --- | --- | --- | --- |
| 单机默认 Compose（本次实测） | 约 45 条/秒 | 2,700 / 13,500 | — |
| 单机，只调环境变量（本次实测） | 约 100–110 条/秒 | 6,000 / 30,000 | 池 64、通道 64 |
| 3 API 副本 + PostgreSQL 16 核 + ClickHouse 16 核 + Redpanda 3 节点 + EMQX 3 节点 | 约 400–500 条/秒（推算） | 2.4–3 万 / 12–15 万 | PgBouncer；`max_connections` 足够；EMQX `nofile` 放开；解决第 4 节 #1、#2 |
| 同上 + ClickHouse 2 分片 + 更多 API 副本（≤12） | 约 700–1,000 条/秒（推算） | 4–6 万 / 21–30 万 | 另需修复第 6 节中的逐条同步写与 ClickHouse 查询问题，否则 PostgreSQL 行锁与往返延迟先到上限 |

- 告警翻转比例高时，以上数字约减半；AI 自动研判不会随集群提高，需按模型并发单独规划。
- 连接规模：3 节点 EMQX（每节点 8 GB、放开 `nofile`）按实测 28 KB/连接推算可承载 50 万级连接；但若平台 MQTT 接收仍为每副本 25 条/秒，报文吞吐会先成为瓶颈。
- 管理端：单 API 的 `events` 与总览是最先饱和的读接口；多副本可线性分担 CPU，但 `events` 的 16 MB 负载会先耗尽网络带宽。

**不修改代码时，集群规模扩大的收益被三件事封顶：** 全局登记锁、PostgreSQL 单主连接数与行锁、平台 MQTT 接收速度。要达到十万级设备、每分钟上报，需要先完成第 6 节的高优先级修改，再在目标集群上按 [容量压测方案](CAPACITY_TEST_PLAN.md) 重测。

## 8. 复现要点

1. 使用与生产隔离的环境（本次：`compose.local.yaml` 全新数据卷），确认 `127.0.0.1` 的依赖端口确实指向该环境；本机有其他虚拟机转发相同端口时会误连。
2. 在仓库根目录编译 release 二进制并启动：`go build -o <输出目录>/iot-platform ./cmd/iot-platform`，然后 `<输出目录>/iot-platform --env-file .env.local`。
3. 通过 `POST /api/v1/onboarding` 使用标准协议（`iot-standard@1.0.0`）创建 HTTP / MQTT 产品，再用 `go run ./cmd/capacity-test -mode provision` 批量登记设备并保存凭据；创建“`stressAlarm` 等于 1 触发、等于 0 恢复”的规则用于告警风暴。
4. 按第 3 节的场景用 `cmd/capacity-test` 的对应模式分别加压（命令示例见 [容量压测方案](CAPACITY_TEST_PLAN.md#分阶梯压测工具-cmdcapacity-test)）；每档记录接收结果、`/metrics` 中的 `raw_archive_success_total`、`parse_success_total`、`kafka_lag_*`、`mqtt_inbox_pending`，以及 `docker stats`。MQTT 场景额外记录 `emqx ctl clients list` 中平台会话的 `dropped_msgs`。
5. 调优配置只需进程环境变量：DSN 追加 `&pool_max_conns=64`，`IOT_KAFKA_CONSUMER_CONCURRENCY=64`；各副本连接池之和不得超过 PostgreSQL `max_connections`。
