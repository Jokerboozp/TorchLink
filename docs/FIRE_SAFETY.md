# 排班、灭火器与消防站管理

三个页面位于“消防管理”。先在“消防站管理”登记站点、人员和器材，再创建班次、排班及灭火器台账。人员是独立业务资料，可以没有平台登录账户；登记人员不会创建账户或授予权限。

## 排班与换班

- 班次模板保存 `HH:mm` 起止时间，结束时间不晚于开始时间时建议次日结束。排班保存实际起止时间戳，可调整模板建议的时间，单次时段最多 48 小时。
- 月 / 周日历按相交时段查询，跨午夜和跨月的排班仍显示。日历与分页列表使用独立查询；日历数据未全部加载时显示提示，可继续加载。
- 每次排班选择一个消防站和一个或多个人员；人员必须启用并属于该站。同一人员的时段不得重叠，相邻时段可以衔接。
- 换班申请指定原排班、原人员、替班人员及原因。审批通过时重新检查原人员仍在班、替班人员归属和时段冲突，再原子替换人员。申请人不能审批自己的申请；驳回不改变原排班。
- 排班存在待审批或历史换班记录时禁止删除，避免丢失关联证据。

## 灭火器台账与巡检整改

台账记录编号、所属消防站、位置、类型、规格、厂家、出厂日期、维保到期日期、报废日期、巡检周期和状态；每个灭火器必须关联一个已登记消防站。日期与周期由现场管理者按器材要求填写，平台不内置法规规定的使用年限。

列表提供维保、报废和巡检到期提示。默认提前 30 天，可通过 `remindDays` 调整为 0 至 365 天。日期在服务进程的本地时区按自然日计算：当天到期属于“即将到期”，次日才属于“已逾期”。巡检周期从最近合格检查或整改通过的复核时间重新计算；尚无合格记录时从台账创建日期开始计算。已报废资产不再显示到期提醒。

巡检任务指定灭火器、责任人员、截止时间和备注。一个灭火器同时最多有一个未结任务。责任人是现场管理资料，提交和审批权限仍由当前登录账户控制。

| 当前状态 | 操作 | 后续状态 |
|---|---|---|
| 待巡检 `pending` | 提交逐项检查，全部合格 | 已完成 `completed` |
| 待巡检 `pending` | 任一项不合格，并填写问题 | 待整改 `rectifying` |
| 待整改 `rectifying` | 提交整改措施 | 待复核 `reviewing` |
| 待复核 `reviewing` | 另一账户复核通过 | 已完成 `completed` |
| 待复核 `reviewing` | 复核驳回并说明原因 | 待整改 `rectifying` |

每次整改及其复核结果都保留，整改提交人不能复核自己的提交。巡检结果由检查项计算，客户端不能自行将异常标为合格。已有巡检历史的资产禁止删除；报废或转移不能破坏未结任务。取消任务必须填写原因，已完成任务不能取消。

## 消防站与出勤

- 站点记录编号、类型、地址、经纬度、联系人及启用状态。经纬度用于维护位置资料。
- 人员记录岗位、联系方式和归属；器材记录类别、数量、单位和可用 / 维护 / 报废状态。灭火器使用独立台账，不自动重复生成器材库存。
- 出勤选择站内人员及器材数量，登记时间、地点、类型和事项。人员未归队时不能再次出勤；器材占用数量不得超过当前可用库存，并发登记也执行这些检查。
- 归队填写时间和总结，释放人员及器材占用。归队不能早于出勤或晚于当前时间；已归队记录不能重复提交。
- 统计展示站点、人员、未报废器材数量、当前出勤和已归队记录；出勤记录可按时间范围查询。当前未归队数量不受历史时间范围影响。
- 存在关联资料或历史记录时禁止删除对应站点、人员或器材；停用及转移也检查未结束排班、出勤和巡检。

## 接口与权限

租户从登录令牌取得，所有关联 ID 都在同一租户内验证。这些独立消防管理资料没有关联 IoT 设备，不授予或扩大任何设备数据范围。

| 菜单权限 | 资源接口 | 主要操作 |
|---|---|---|
| `menu:duty` | `/api/v1/duty/shifts`、`/api/v1/duty/assignments`、`/api/v1/duty/swaps` | 模板与排班增改删；申请换班；`POST /api/v1/duty/swaps/:id/review` 审批 |
| `menu:extinguishers` | `/api/v1/extinguishers`、`/api/v1/extinguisher-inspections` | 台账增改删；建任务；检查、整改、复核、取消使用 `POST /api/v1/extinguisher-inspections/:id/` 加 `inspect`、`rectify`、`review`、`cancel` |
| `menu:fireStations` | `/api/v1/fire-stations`、`/api/v1/fire-personnel`、`/api/v1/fire-equipment`、`/api/v1/fire-dispatches` | 站点人员器材增改删；建出勤；`POST /api/v1/fire-dispatches/:id/return` 归队 |

GET 读取要求对应菜单；每个写操作还要求精确的方法和路由权限。管理员可在“用户与权限 → 消防管理”分别授权查看、管理或自定义操作。

`GET /api/v1/fire-safety/options` 供三页共享选择器，只返回站点和人员的编号、名称、归属、启用状态；班次、灭火器和器材选项还分别要求对应菜单。不返回电话、地址、检查或审批历史。

列表使用 `page` / `pageSize`，每页最多 100 条；支持 `q`、`stationId`，具有流程或资产状态的资源支持 `status`（站点、人员的启用字段为 `enabled`，没有对应的列表筛选参数）。排班的 `fromAt` / `toAt` 为左闭右开的相交时间窗；巡检按截止时间、换班按申请时间、出勤按出勤开始时间筛选。灭火器可用 `due=overdue|soon` 筛选：有逾期项目归入 `overdue`，其余有即将到期项目归入 `soon`。

`GET /api/v1/fire-stations/statistics` 和 `GET /api/v1/extinguishers/statistics` 提供统计。灭火器统计的到期数量按资产去重，同一资产有逾期项目时不重复计入“即将到期”。

PUT 及已有记录的审批、检查、整改、取消和归队操作必须提交当前记录的 `version`；DELETE 使用 `?version=<当前版本>`。过期编辑、重复流程操作、库存或排班冲突返回 409；自审批返回 403。应刷新后重新操作。

## 持久化

生产仓储把三个模块保存在 PostgreSQL `platform_fire_safety` 表，每租户一个 JSONB 聚合记录。启动沿现有迁移流程创建表；租户 revision 的比较写入将关联检查、排班冲突、器材占用和业务修改作为一个原子提交。冲突重试时重新校验，记录 version 防止过时编辑覆盖。memory 实现用于测试与内存运行模式，不能代替 PostgreSQL 持久化。

部署迁移及数据库备份边界见 [部署指南](DEPLOYMENT.md#数据库迁移) 和 [备份范围](DEPLOYMENT.md#设备数据备份)。

主要源码入口为 `internal/firesafety/`、`internal/httpapi/fire_safety.go`、`internal/adapters/{memory,postgres}/fire_safety.go` 及三项前端页面。

源码回归、PostgreSQL 联调条件与浏览器核对入口统一见 [消防管理回归](DEVELOPMENT.md#消防管理回归)。
